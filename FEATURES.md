# Graphiq Studio — Features & Architecture

A browser-based, **fully client-side** raster photo editor with a non-destructive layer stack. There is no server, database, or upload — images never leave the machine; everything is computed in the browser on HTML `<canvas>` elements.

**Stack:** Next.js 16 (App Router) · React 19 (with the React Compiler) · TypeScript (strict) · SCSS modules · `lucide-react` icons. **No image-processing libraries** — every pixel operation (compositing, blending, blurs, filters, tone curves, selections, layer effects, history) is hand-written against the Canvas 2D API and `ImageData`.

**Status:** the destructive editor (19 tools, 19 blend modes, selections, live sessions, colour management) plus the **full non-destructive stack** — layer **masks**, **adjustment layers**, **layer effects**, **Curves & Levels**, **clipping masks**, **smart filters**, and the **render-graph cache**. Project files (`.gproj`, formerly `.aproj` — old files still open) are at **format version 20** (v8 filter masks, v9 metadata, v10 colour labels, v11 stored paths, v14 fill layers, v18 saved selections, v19 vector masks). See [Part 3 — Known limitations](#part-3--known-limitations--not-yet-implemented) for what's partial or absent.

This document is written so someone **without the code** understands exactly what exists, what works, **how** it works, and what does not.

# Part 1 — Feature inventory

## Documents & canvas

- **Multiple documents** open as renamable tabs. Each tab is fully independent: its own layer tree, undo history, selection, view (zoom/pan), working colour space, and metadata.
- **New / Open (.gproj) / Import (image)**; arbitrary canvas sizes.
- **Image Size** (resample — content scales) vs **Canvas Size** (reframe — content stays, the frame grows/shrinks).
- **Rotate 90° CW/CCW**, **Flip Horizontal/Vertical** (whole image).
- **Crop** (interactive box: aspect presets, rule-of-thirds/grid overlay, straighten, shield) and **Trim** (auto-remove uniform border pixels).

All Options-Bar settings, the foreground/background colours, and the marquee shape + triangle apex **persist to `localStorage`** and restore on reload.

## Selections

- The selection model is a **list of rectangles** plus an optional rotation **angle + pivot**. Freeform/curved regions (wand, ellipse, triangle, lasso) are rasterised to per-row scanline rects and merged by the engine's **mask-based combine**, which returns clean **pre-traced marching-ant outlines** — so even a 500-rect ellipse animates its ants cheaply (no per-frame O(n³) boundary union).
- **Add (Ctrl) / Subtract (Alt)** while dragging; the existing selection stays visible during the drag and the new region previews separately.
- **Select menu:** All `Ctrl+A`, Deselect `Ctrl+D`, Reselect `Ctrl+Shift+D`, Inverse `Ctrl+Shift+I`, **Feather…** `Shift+F6`, **Grow…** (Feather blurs the selection mask for fills/deletes/moves; Grow expands the region by N px).
- **Free Transform** `Ctrl+Alt+T` and **Transform Selection** `Ctrl+Alt+Shift+T` — scale/rotate either the pixels or just the outline, with corner/edge handles, a rotation ring, and a movable pivot.
- Fill with foreground/background (`Backspace`/`Delete`), Cut/Copy/Paste of selected pixels.
- **Arrow-key nudge:** with a selection tool, arrows move the **outline** by 1 px (`Ctrl` = 10 px); with the Move tool, arrows move the **pixels** (selection content, the whole layer — linked mask included — or a floating paste), and a rapid burst of presses lands as a single undo step.
- **Content-Aware Fill** (`Shift+F5`, Edit menu): fills the selection with content synthesized from its surroundings — overlapping source blocks blended with a seamless tone-matching pass — as one undoable step.
- **Save / load selections (alpha channels):** **Select ▸ Save selection…** stores the current selection as a named grayscale channel that lives with the document, and **Load selection…** brings it back — as a new selection, or combined with what's already selected (**Add / Subtract / Intersect**). Saved selections appear in the **Channels panel** under *Saved selections*, each with a thumbnail of its coverage: click a row to select it, **Ctrl** to add, **Alt** to subtract, **Ctrl+Alt** to intersect (the same modifiers the Paths panel uses, because they do the same job to the same selection). Double-click a name to rename, and the trash icon deletes — both undoable. Channels are saved inside the `.gproj` (v18) as grayscale PNGs, so a laboriously-built selection survives closing the file. A channel whose raster is missing from a file is dropped rather than loaded as an empty selection.
- **Quick Mask mode** (`Q`, or Select ▸ Quick Mask mode): paint a selection instead of dragging one. Entering turns the current selection into a grayscale raster, clears the selection so brushes aren't clipped by it, and shades everything unselected in the classic **rubylith red**; paint black to mask more, white to select more, and `Q` again turns the coverage back into a real selection. A soft brush therefore yields a **feathered selection**. Every paint tool edits the mask — fills, the gradient, blur and dodge included — and the document's pixels come out byte-identical, because the red is an overlay and the mask composites into nothing. Entering with no selection starts from *everything selected* (no red), matching the app-wide rule that an empty selection means the whole document is editable; exiting with full coverage symmetrically gives no selection rather than a full-canvas marquee. The raster survives leaving the mode, so undoing the exit puts you back inside it exactly as you left it and the strokes within then undo visibly. Each document keeps its own quick mask across tab switches.

## Layers

- A **tree** of three node kinds: **pixel layers** (`LayerLeaf`), **groups** (`LayerGroup`, nestable folders), and **adjustment layers** (`LayerAdjustment`, pixel-less — see below).
- Per-node **visibility, opacity (0–100), blend mode** (19 modes), an optional **mask**, optional **layer effects**, and a **clipped** flag.
- **New / Duplicate / Delete / Group (`Ctrl+G`) / Ungroup / Merge Down (`Ctrl+E`) / Flatten**. Drag to reorder (can re-parent across groups). Multi-select. Inline rename.
- **Colour labels + filter row:** tag any node with one of **seven colour labels** (right-click menu swatches, applies to the whole selection, shown as a dot on the row, saved in `.gproj` v10) and filter the panel by **name, kind and label** — matches stay bright while their ancestors dim for context, a matching group reveals its contents (even inside collapsed groups), and drag-reorder pauses while a filter is active so hidden hierarchy can't be rearranged blind.
- **Lock flags:** a Lock row on every node — **transparency** (paint only where pixels already are), **pixels** (block every pixel edit), **position** (block moves) and **all**. Enforced at the engine's commit chokepoint rather than per tool, so nothing can slip past; a blocked action explains itself instead of silently doing nothing.
- **Linked layers:** link sets that move together without being grouped — link two or more nodes (chain icon) and dragging, nudging or transforming any of them carries the rest by the same delta, with their masks along for the ride. Independent of grouping, so a link can cross group boundaries.
- **Fill layers:** parametric **Solid Colour** and **Gradient** layers that hold no pixels — re-edit the colour or the whole gradient (type, stops, angle, reverse) any time from the Layers panel or Properties, at any canvas size. They take masks, blend modes, opacity, clipping and layer effects like any other node. (Pattern fills remain a follow-up.)
- Group **opacity/blend/mask** apply to the *merged* group result (isolated grouping), exactly like Photoshop.

## The non-destructive stack

These five systems are the heart of the editor. They are all **composite-time**: they change how the layer tree is rendered, never the stored pixels (except an explicit "Apply/bake").

### 1. Layer masks
- Any pixel layer **or group** can carry one **grayscale raster mask** (white = visible, black = hidden, grey = partial). It modulates the layer's alpha at composite time; the layer's own pixels are never altered.
- **Create** reveal-all / hide-all / from-selection; **Delete**; **Apply** (bake into the layer, destructive); **Enable/Disable**; **Link/Unlink**; **Load Mask as Selection**.
- **Active-surface switch:** click a layer's mask thumbnail to make the mask the paint target; click the pixel thumbnail to switch back. **Every paint tool then edits the mask** — brush, pencil, eraser, clone, paint bucket, gradient, **blur and dodge/burn**, plus Backspace-fill and Delete.
- **Linked move:** with the chain (link) toggle on, moving the whole layer moves its mask with it — one undo step restores both.
- Layers panel: mask thumbnail beside the pixel thumbnail, an **active-surface ring**, a chain (link) toggle, Shift-click to disable; Layer menu has the full submenu; the **Channels** panel and the masking interact correctly (mask multiplies the *final* styled result, so a mask also hides a layer's effects).
- **Mask view (Alt-click) + mask channel:** **Alt-click a mask thumbnail** to see the mask itself grayscale on the canvas (Photoshop-style — its effective value, live even while painting it; the chip gets a dashed accent ring, and viewing also targets the mask for painting). Click any thumbnail — or Alt-click again — to return. The **Channels panel** shows the active layer's mask as a fourth channel: a toggleable grayscale tonal curve (own normalization) beside R/G/B, plus an eye button that drives the same on-canvas mask view. The view is session-only and resets on document switch.

### 2. Adjustment layers
- A **`LayerAdjustment`** node holds an **`AdjustmentSpec`** and **re-processes the composite of everything below it** within its parent — non-destructively, re-editable forever.
- Types (all routed through the existing `applyAdjustments` math so there is one colour engine): **Brightness/Contrast, Exposure, Vibrance, Color Balance, Black & White, Photo Filter (Warm/Cool)**, the named **filter presets** (Vivid/Noir/Vintage/…), and **Curves / Levels** (below).
- **Extra adjustment kinds** (own pixel math in `adjust-extra.ts`, same node semantics): **Hue/Saturation with per-range targeting** (Master + six feathered hue-wheel ranges — reds/yellows/greens/cyans/blues/magentas — each with hue/saturation/lightness; greys are never range-targeted), **Selective Color** (nine Photoshop-style ranges with relative/absolute CMYK deltas), **Gradient Map** (composite luminance through the shared gradient editor, reversible), **Channel Mixer** (per-output-channel linear mixes + constant, monochrome mode), **Color Lookup** (imports a **3D `.cube` LUT**, applied with trilinear interpolation; the LUT rides inside the `.gproj`), and **Invert / Equalize**. All are strictly per-pixel — so they keep the render graph's region-scoped and tiled recompute — **except Equalize**, whose whole-image histogram the engine detects and always recomputes in full. Parameterized kinds edit in a live dialog (one undo step per gesture, like Curves). Created from **Layer ▸ Adjustment ▸ {type}** or the **Adjustments panel's** button grid below Curves/Levels.
- **LUT export (.cube)**: the current grade exports as a standard 3D LUT (File ▸ Export LUT (.cube)… or the Adjustments panel's "Export as LUT" button) — either the **visible adjustment-layer stack** (bottom→top with opacity + blend modes) or the **panel's current sliders**, sampled through the exact compositor math over a 17³/33³/65³ identity lattice. The dialog reports what can't travel into a LUT (Equalize, masks/clipping, group-nested adjustments, spatial sharpen/noise). Exported LUTs round-trip through the app's own Color Lookup adjustment and work in any .cube-reading software.
- Honours its own **opacity, blend mode, mask, and clip**. Created from **Layer ▸ Adjustment ▸ {type}** or the **Adjustments panel** ("Create Adjustment Layer", "Curves", "Levels"). Editing is **live with no Apply step**; one cheap, params-only undo step per edit gesture.
- The destructive Adjustments-panel path (live preview on a pixel layer + the slider set) still exists; a **"Create adjustment layer"** button converts that preview into a node.

### 3. Layer effects (layer styles)
- Eight non-destructive effects rendered from the layer's **alpha silhouette** at composite time: **Drop Shadow, Inner Shadow, Outer Glow, Inner Glow, Stroke** (solid colour or a full **multi-stop gradient** with reverse + angle), **Color Overlay, Gradient Overlay, Bevel & Emboss** — each with its own blend mode + opacity.
- A **Layer Style dialog** (left column = effect checklist, right column = per-effect controls, with a **live document preview**) reusing the app's custom colour picker. **Copy / Paste / Clear Layer Style**; an **fx badge** + footer button + context menu in the Layers panel.
- Shadows/glows use the **shared separable blur** (the same primitive as the Blur Gallery). Effects render in the correct stacking order and compose with masks, adjustments, opacity, blend, and groups.

### 4. Curves & Levels
- **Curves:** a **monotone-cubic** spline (Fritsch–Carlson — guaranteed monotonic, no overshoot) over a live histogram backdrop, per channel (RGB/R/G/B); click to add a node, drag to move, right-click to delete; numeric input/output readout; **presets** (Linear, Increase/Decrease Contrast, Negative, Lighten/Darken Midtones).
- **Levels:** input black/gamma/white + output black/white as **draggable triangles** over a live histogram, per channel, with numeric fields, **Auto** (per-channel contrast stretch), and **black / grey / white eyedroppers** (click the image to set the point or neutralise a colour cast).
- Both compile to **per-channel 256-entry LUTs** (composite⊕channel composed, alpha untouched) applied in one typed-array pass. Available **non-destructively** (as adjustment layers, re-editable via the dialogs) and **destructively** (Image ▸ Adjust ▸ Levels/Curves… → live preview → Apply/Cancel).

### 5. Clipping masks
- Any leaf, group, or adjustment can be **clipped** to the layer directly below it (its *base*): it shows only within the base's silhouette. A **clip group** = a base + the contiguous run of clipped layers above it.
- Members **blend within the group**; the base's opacity/blend/mask then govern the whole group against the layers below. Toggle with **`Ctrl+Alt+G`**, **Alt-click a layer row**, or the context menu. The Layers panel shows clip groups **indented with a ↳ elbow** under an **underlined base name**.
- **Clipping through adjustments (Photoshop-faithful):** a clipped layer sitting directly above a *non-clipped* adjustment layer isn't inert — it walks down past the adjustment run and clips to the first pixel layer/group beneath, while still rendering **above** the adjustments (so they affect the base but never the clipped content). Clipped runs, blends against the adjusted backdrop, and clipped adjustments inside such runs all behave; a clipped node with nothing to borrow (bottom of the stack, only adjustments below) stays inert.

## Adjustments & filters (destructive panel)

- **Adjustments panel** previews live on the active layer (no Apply button — it auto-bakes on session end; Reset discards): **Light** (exposure, contrast, highlights, shadows, whites, blacks) · **Colour** (temperature, tint, vibrance, saturation) · **Detail** (sharpen, clarity, noise).
- **Filter presets** (Original, Vivid, Mono, Noir, Warm, Cool, Vintage, Fade) and **custom presets** that **import/export** to `.gifp`/`.gifpack` files.

## Effects (Blur Gallery)

- **Effects ▸ Blur Gallery…** — a large dialog with an embedded **live-preview canvas**: **Box, Gaussian, Motion, Zoom, Spin, Bokeh**. Zoom/Spin have a **draggable centre point**. Scope = selection (if any) or the whole layer/canvas.

## Colour, file, panels, view, UI

- **Colour:** primary/secondary swatches (remembered), swap & reset, alpha-aware over a checkerboard; a custom **colour picker** + popover used everywhere (options bar, gradient, layer styles); **Compare Colour Profiles** dialog; colour-management dialog.
- **Colour management:** working spaces **sRGB**, **Display P3** (native canvases, browser-managed), and **Adobe RGB (1998) — emulated**: pixels stay on an sRGB canvas (a browser cannot display or export an Adobe RGB canvas), while slider adjustments, adjustment layers and Curves/Levels matrix-convert into Adobe RGB primaries, run their math there, and convert back — matching how those edits behave in an Adobe RGB workflow. Colours outside sRGB still clip at the canvas, and filters/effects/compositing remain in the canvas space; switching to or from the emulated space is lossless. The Color Management dialog states all of this.
- **Soft proofing:** **Proof colors** (`Ctrl+Alt+Y`) simulates how the document will look in a target space (sRGB / Display P3 / Adobe RGB — chosen in Color Management, persisted) on the view only; **Gamut warning** (`Ctrl+Alt+Shift+Y`) marks colours outside the target's gamut in mid-grey. In-gamut pixels display byte-identically; exports are never proofed. Most useful on Display P3 documents proofed against sRGB before an sRGB export.
- **RAW (DNG) development — hand-written decoder:** importing a `.dng` runs a true raw develop, not just the embedded preview: TIFF/IFD parsing, **uncompressed** (16-bit or packed 10/12/14-bit) and **lossless-JPEG (SOF3)** CFA data in strips or tiles, then black/white-level normalization → as-shot white balance → camera→sRGB colour matrix → baseline exposure → sRGB gamma with bilinear demosaic, ActiveArea/DefaultCrop and orientation — all dependency-free, decoded off-thread in a worker. DNGs outside the subset (lossy-JPEG/JXL, float HDR) and other RAW formats (CR2/NEF/ARW…) fall back to the embedded JPEG preview as before.
- **ICC profile import (assign vs convert):** imports sniff embedded ICC profiles from the file bytes (PNG/JPEG/WebP) and show the profile's name; when it differs from the working space, the Import dialog offers **Convert** (colour-managed decode — keeps appearance, the default) or **Assign** (decode without colour management — keeps the raw numbers). Untagged images and same-space profiles skip the question.
- **PSD interchange — hand-written reader + writer:** importing a `.psd` opens it as its own **layered document**: layers (RAW/RLE channel data), **nested groups**, **layer masks** (with disabled flags), opacity, blend modes, **clipping masks**, visibility and unicode names all survive; text and smart objects arrive as their rasterized pixels; adjustment/fill layers are skipped with a note. Files outside the subset (16/32-bit, CMYK, no layer data) import as the flattened composite instead of failing; PSB is rejected with a clear message. **File ▸ Export PSD (layered)…** writes the whole tree back out — groups as section dividers, masks, opacity/blend/clipping/hidden flags, RLE-compressed channels, the document's ppi, and the required flattened composite (over white) so even layer-ignorant readers show it. The writer's output round-trips byte-exactly through the reader (verified: pixels, masks, structure, all 18 blend modes).
- **TIFF import + export — hand-written codec:** importing a `.tif` decodes it in-app (Chrome/Firefox can't decode TIFF at all): both byte orders, strips **and tiles**, **8/16-bit** samples (16-bit shown at 8 for now), grayscale (both polarities), palette, RGB(A) with associated-alpha un-premultiply, **PackBits / LZW / Deflate** compression with the horizontal predictor, orientation and dpi — verified pixel-exact against a real codec's LZW output (GDI+). Files outside the subset (JPEG-in-TIFF, CCITT fax, float, planar) fall back to the browser/preview path. **File ▸ Export TIFF…** writes the flattened composite as 8- or 16-bit RGB(A) with Deflate-compressed strips, straight alpha or white-matted, plus resolution tags — 16-bit is the 8-bit canvas widened (v·257) for 16-bit pipelines, stated in the dialog. **HEIF/HEIC** imports decode where the browser ships the codec (Safari; most others don't) — undecodable files now get a named alert saying exactly that — and the Metadata panel reads **EXIF out of HEIF and AVIF** containers via an ISO-BMFF scan.
- **PDF export — hand-written writer:** **File ▸ Export PDF…** writes a single-page PDF 1.4 from the flattened composite: page sized to the image at a chosen ppi, or to **A4/Letter/Legal/A3/A5** (portrait/landscape) with an mm margin — **fit to margins** or actual-size-at-ppi, centred, with an overflow warning. The image embeds as **JPEG (DCTDecode)** with a quality knob or **lossless (FlateDecode)**; transparency mattes over white; the Info dictionary carries title, author (doc metadata artist or the Preferences attribution default), creator and a timezone-correct creation date (Unicode-safe). Structure Node-verified: xref offsets, stream payloads, escaping.
- **SVG import (vector layers) + SVG export:** importing an `.svg` parses it with the browser's own machinery (a hidden shadow-DOM mount, so transforms/viewBox come from `getScreenCTM` and styles from the full CSS cascade) into a **vector layer** — styled path recipes that rasterize crisply from the source geometry (`vector: path` recipe on the layer, kept in `.gproj`, shown as "Vector layer" in Properties). Covers paths, rects/circles/ellipses/lines/polylines/polygons, groups, transforms, fill rules, stroke caps/joins/dashes and per-paint opacity; files using features beyond that subset (text, gradients/patterns, filters, masks, clip-paths, markers, `<use>`…) import as a faithful **raster** of the browser's own rendering instead — never a degraded "vector". The pixels of a vector import are rendered from the recipe itself, so the recipe and the layer can never disagree. **File ▸ Export SVG (vector layers)…** serializes every visible vector-bearing layer — imported vectors as paths, **shape layers through the exact ring geometry the rasterizer paints**, **text layers through the same line layout** (wrap, alignment, leading, tracking, decoration) — with layer opacity and CSS-mappable blend modes; raster/adjustment layers are skipped and counted in the toast.
- **High-bit adjustment path:** in the emulated Adobe RGB space the whole adjustment pipeline runs at **16 bits/channel** — canvas bytes decode straight to Adobe RGBA16, slider math and 65 536-entry tone/curve LUTs run on 16-bit values, and a single final quantization writes back to the 8-bit canvas (the compositing fallback). Identity edits roundtrip byte-exact — verified numerically. Native sRGB/P3 spaces keep the plain 8-bit path, which already quantizes only once per pass.
- **HDR — merge, tone map, true-HDR export:** **File ▸ Merge to HDR** fuses 2+ bracketed exposures (tripod-aligned, same pixel size) into a **32-bit float radiance map** — EVs auto-read from EXIF (`log2(N²/t) − log2(ISO/100)`) or estimated from brightness, hat-weighted Debevec-style merge that drops clipped channels and recovers highlights from the darkest frame (Node-verified against synthetic brackets to <1% error). A live tone-mapping stage (exposure ±4 ev; **Filmic/Hable**, **extended Reinhard**, or linear) renders the new document, which **keeps the float source in memory**: **Image ▸ HDR tone mapping** re-renders the active layer from float any time (one undo step, no cumulative 8-bit loss), and **File ▸ Export HDR PNG** writes a genuine HDR file — a hand-written **16-bit PNG** encoder (zlib via `CompressionStream`, CRC-verified) tagged **Rec.2100 PQ or HLG via a `cICP` chunk** (BT.2020 primaries, SDR white at 203 nits, PQ peak configurable), whose highlights render beyond SDR white on HDR displays; the dialog reports whether the current display has HDR headroom (`dynamic-range: high`). Honest limits: no auto-alignment, the float map isn't persisted in `.gproj`, and the canvas itself stays SDR.

## The paint engine

`PaintEngine` (`paint.ts`) owns one offscreen `<canvas>` per pixel layer (a `Map` keyed by layer id), plus several reusable buffers:

- **`stroke`** — the in-progress brush dab/stroke (kept **sRGB**, see Colour).
- **`scratch`** — live-session previews.
- **mask buffers** — `masks` (grayscale mask per id) and `maskAlpha` (derived alpha cache per id) Maps.
- **adjustment/clip buffers** — a small pool (`adjBufs`) including the offscreen composite **accumulator**.

### Live "session" model
Almost every gesture is a temporary, cancellable session that snapshots the original pixels, shows a live result, and **bakes once on commit** (one history entry). Independent sessions exist for: **paint stroke** (brush/pencil/eraser), **blur brush** and **dodge/burn** (a *coverage-mask* model — original snapshot + a 0–1 coverage buffer re-baked as `mix(orig, effect(orig), coverage×strength)`, so a stroke stays even and successive strokes compound), **clone**, **move/float**, **live shape**, **live gradient**, **live pen path**, **live bucket fill**, **live (destructive) adjustment**, **destructive tone** (Curves/Levels via `previewTone`), and the **Blur Gallery** preview.

The brush **tip is pre-baked once per stroke** (hard tips crisp on the integer grid, soft tips sub-pixel); eraser = `destination-out`.

## The compositor (the core)

`composite(tree)` renders into an **offscreen accumulator** (`willReadFrequently`, so adjustment layers can read it back) and then blits to the on-screen view canvas. `exportComposite(tree)` does the same into a fresh buffer for flatten/export. Both call **`drawStack(ctx, nodes)`**.

```
drawStack(ctx, nodes):
  for unit in clipGroupsOf(nodes)        // bottom → top, clip groups resolved
    if unit has clipped members:  renderClipGroup(ctx, unit.base, unit.members)
    else if base is adjustment:   applyAdjustmentNode(ctx, base)   // reads what's beneath in ctx
    else:                         drawNode(ctx, base)
```

**`drawNode`** draws one ordinary leaf/group:
```
src = styledSource(node)                 // leaf pixels (+ effects) OR group merged buffer (+ group effects)
src = maskedSource(node, src)            // destination-in the node's mask alpha cache (if any)
ctx.draw(src) with opacity + blendOp(blend)
```
- **`styledSource`** → a leaf's display canvas (run through `styledLeaf` if it has effects), or a group's `groupMerged` (children composited via `drawStack` into a fresh buffer + the group's own effects).
- **`leafDisplay(id)`** is the live-preview indirection: normally the layer canvas, but during a live session on that layer it returns the `scratch` buffer with the layer + in-progress edit — so previews composite correctly under blend modes/opacity without touching real pixels.
- **`maskedSource`** multiplies the node's mask in with a single `destination-in` of the cached alpha (no per-pixel JS).

**`applyAdjustmentNode(ctx, node)`** (for an adjustment that is *not* a clip member): reads the accumulator beneath it (`getImageData`), runs `applyAdjustments` (sliders) **or** the cached tone LUTs (Curves/Levels), then writes the result back **modulated by the node's opacity × its own mask** and blended with its blend mode. A neutral spec is a no-op. Group isolation is automatic because a group's children composite into the group's own buffer.

**`renderClipGroup(ctx, base, members)`** (the clip-group assembly):
```
1. render base (masked) into a FRESH buffer cg          // nesting-safe; not pooled
2. clipAlpha = snapshot of cg's alpha (the base silhouette, post-mask)
3. for each visible member (bottom→top):
     adjustment → applyAdjustmentNode(cg, member)        // processes the base-shaped buffer
     else       → draw member (its effects, mask, blend, opacity) onto cg
4. cg ⊗= clipAlpha   (destination-in)                    // clip the whole group to the base
5. draw cg onto ctx with the BASE's opacity + blend mode
```
This single path also subsumes "clipped adjustment layer" (Spec 02's old standalone clip-base logic was deleted).

**Blend modes (19)** map to Canvas 2D `globalCompositeOperation`. A few are pragmatic approximations: **Add→`lighter`**, **Linear Burn→`multiply`**, **Dissolve→`source-over`** (no true dither). Hue/Saturation/Color/Luminosity use the non-separable canvas modes.

## How the non-destructive features are implemented

- **Masks:** the grayscale mask is colour-agnostic (always sRGB, never gamut-converted). On any mask edit the **alpha cache** is re-derived **scoped to the changed rect** (`A = R × maskAlpha/255`, RGB=0). A `surfaces` map records each layer's active paint surface; `surfaceTarget(id)` is the single chokepoint that points the brush/fill/gradient at the layer canvas **or** the mask canvas. A live mask brush previews through `maskDisplay(id)`. History pixel entries carry a `surface: 'layer' | 'mask'` field. Canvas resize/crop/rotate/flip transform masks in lockstep with their layers.
- **Adjustment & tone:** **params live entirely on the tree** — the engine holds no canvas for an adjustment node; it just reads them while compositing. Tone LUTs are cached per node id + spec hash (`toneCache`).
- **Effects:** rendered by the pure `renderStyled(src, fx, space)` (document-sized buffer). The styled buffer is **cached per layer** keyed by `pixelVersion | colourSpace | docEpoch | fxHash` (`effectsCache`) — re-rendered only when the layer's pixels, its effect params, the colour space, or the document geometry change; **bypassed (re-rendered each frame) only while that layer is being painted**.
- **Clipping:** `clipped` is a boolean on every node; membership is **derived each composite** by `clipGroupsOf(children)` (never stored). A clipped node with no valid base below is **inert**.

## History (undo/redo)

An **undo tree** of `Entry` objects + a position pointer. Every entry records the state it was made on top of, so moving between any two states walks back to their common ancestor and forward again; with non-linear history off the tree is pruned to a single line and behaves exactly like the linear stack it grew out of.
- **Pixel entry:** `layerId`, a bounding `rect`, `before`/`after` `ImageData` (only the changed region), and a `surface` (layer vs mask).
- **Structural entry:** a `side` with `undo()`/`redo()` callbacks for tree changes (add/remove/group/merge/crop/resize/paste, mask add/apply, **adjustment param edits, layer-effect edits, clip toggles** — all params-only, no pixel data). Pixel + structural can be combined into one step (e.g. paste, Apply Mask).
- `jumpTo(target)` walks the pointer, reverting/applying entries (pixels via `putImageData`, structure via the `side` callbacks); `undo`/`redo` are ±1; a new edit truncates the redo branch. Live sessions finalise before navigation. A label+index summary drives the History panel.
- Non-destructive edits (sliders, curve points, effect params, clip flags) are **debounced to one undo step per gesture** and carry **no pixel data** — the whole point of non-destructive editing.
- **Non-linear history** (a branch toggle at the top of the History panel): normally, stepping back and then painting throws away everything after where you are. Turn it on and those states are **kept as a branch** — the list shows both, marks the entries that aren't on your current path, and clicking any of them goes straight there, so you can try an idea, step back, try another, and flip between them. Undo/Redo behave as always (Redo follows the branch you were last on); switching the toggle off prunes the branches you left behind. A branch costs one number per step, not a second copy of the document.
- **Snapshots:** pin the whole document (every layer's pixels, its masks, the layer stack, the canvas size) with one click and restore it later as a single undoable step. Unlike stepping back, a snapshot survives further edits — and it doubles as a **History-brush / Erase-to-History source**, so you can paint any part of the image back to how it looked then.
- **Undo memory budget:** the stack is capped by **megabytes** as well as by step count, whichever is reached first. A step count was never a good guide to memory — one full-canvas edit stores the pixels before *and* after, so a single fill on a 1920×1080 document weighs about 17 MB while a hundred small dabs might weigh three. **Preferences ▸ Performance ▸ Undo** has both sliders and a live meter (`6 steps · 79 MB of 512 MB`). Trimming reuses the undo tree's safety rule: abandoned branches go before anything still reachable, and never a step something else depends on. Snapshots stay outside the budget — they are yours until you delete them.
- **History log in the file:** reopening a project shows **what was done to it before** — a collapsible *"12 earlier steps · from the file"* section listing the previous session's edits with repeats grouped (`Brush ×7`). Editing and saving again appends, capped so the log can't grow a project file. It is deliberately a *record*, not a time machine, and the panel says so: a saved file holds its current pixels, not the ones each step replaced, so those states genuinely cannot be travelled to — the rows have no hover, no cursor and no click.

## Layering (tree)

`LayerBase` (shared by all kinds): `id, name, visible, opacity, blend`, optional `mask`, optional `effects`, optional `clipped`. `LayerLeaf` adds an optional `vector` (re-editable shape/text); `LayerGroup` adds `expanded` + `children`; `LayerAdjustment` adds `adjustment: AdjustmentSpec`.

All tree edits are **pure functions returning a new tree** (find, update, remove, insert-relative/into-group, wrap-in-group, ungroup, **clone-subtree** with fresh ids + deep-copied effects, replace, remove-many, merge-down, flatten, multi-select helpers, visible-row order, and the `clipGroupsOf` clip resolver). The engine mirrors structural ops (`duplicateLayer`, `rasterize` for merge/flatten — which now bake masks + adjustments + effects + clipping, since it composites through `drawStack`).

## Colour management

- Per-document **working colour space: sRGB or Display-P3** (feature-detected). Layer/scratch/group/accumulator/export buffers are all in that space, so wide-gamut content is preserved end to end.
- The **brush `stroke` buffer stays sRGB** because brush/UI colours are authored as sRGB hex; compositing onto a P3 layer lets the browser convert correctly. Layer-effect colours work the same way (sRGB hex filled onto a P3 buffer).
- `setColorSpace` converts existing layers by drawing them through a new-space canvas; masks are **not** converted (coverage, not colour); effect/tone caches invalidate.

### Feather preview

- A feathered selection's marching ants mark the **50% line**, which says nothing about how far the softness actually reaches. Two faint outlines now show the edges of the soft band, so "feather 30" is something you can see rather than imagine.
- The offsets come from **stroke geometry**, not from offsetting the polygon: the ant path is stroked at twice the softness and the middle is then carved out with `destination-out`, leaving exactly the inner and outer bounds with the rasteriser doing the offset-curve work — including the corners, which come out correctly rounded on the outside and sharp on the inside. It draws on its own scratch canvas, because that carve would otherwise eat whatever else is on the overlay (the Quick Mask wash, for one), and it is skipped below ~3 screen pixels where it would just fatten the ants.
- The band width is **`effectiveSoftness`, not `feather`**: contrast (and a large shift, through the gain floor) compresses the ramp, so a 20 px feather at 80% contrast is a 4 px soft edge. It shares the exact gain function the pixel pipeline uses, so the preview cannot drift from the maths — drawing the raw slider value would have made the overlay lie precisely where it is hardest to check by eye.

### Vector masks

- **Layer ▸ Vector mask from path** turns the Pen tool's current path into a mask, with **Invert** and **Delete** beside it. A layer can carry a vector mask AND a raster mask at once — they **multiply**, so a pixel survives only where both let it through: the raster mask paints softness and detail, the vector mask cuts a clean, resolution-independent edge.
- The **path stays the source of truth**, not a raster. It is a few hundred bytes in the project file instead of a full-canvas PNG, it re-rasterises crisply at any document size, and it remains re-editable. The engine rasterises it with `Path2D` — the same anti-aliasing every other vector in the app gets — and caches the result keyed by a hash of the anchors, handles, inversion and feather, so moving one anchor re-renders that layer and nothing else. The hash rounds to a tenth of a pixel: finer than any visible change, but coarse enough that float jitter cannot churn the cache every frame. An open path is filled as though closed, because a mask is an area.
- Two fast paths had to learn about it, and both would have silently ignored it: `renderNode` aliases a "plain leaf" straight to its layer canvas when it has no fill, mask, effects or filters, and the masking step itself was guarded on the raster mask alone. A vector-mask-only layer matched both and composited completely unmasked — the feature was correct and simply unreachable. Verified on the composite: a full-canvas fill clipped to a triangle goes 120000 → 27300 opaque px, inverting gives 92700, and **27300 + 92700 = 120000** exactly.
- Persists in `.gproj` (**format v19**) and survives a save/reopen round-trip unchanged (27300 → 27300 px). That needed wiring by hand into all three node branches of the loader, which builds nodes field by field rather than spreading them — a new field is dropped otherwise, and it typechecks either way.

### Transform selection by numbers

- With a selection active, the options bar carries **X / Y / W / H / Angle** fields. They read from the live selection, so they track marquee drags, Modify operations and undo without any separate state — and they disappear when nothing is selected. Each edit is one undo step; rotation turns about the bounding-box **centre**, matching the on-canvas handle.
- The interesting part is that a selection is a LIST of rectangles, not one box. Scaling each rectangle independently and rounding its position and size separately **tears the selection**: two rects that abut exactly can round to a one-pixel gap or a one-pixel overlap, which shows as hairline seams through a filled selection and doubly-composited rows where they overlap. So [selection-transform.ts](app/lib/selection-transform.ts) rounds **edges, never sizes** — both rects derive their shared boundary from the same source coordinate through the same function, so they land on the same integer by construction. Verified on a 12-rect strip scaled by 1.37: zero gaps and zero overlapping pixels, against 200 overlapping pixels for the naive approach.
- Rectangles that scale below a pixel are **dropped rather than clamped** to width 1, or a heavily shrunk selection would grow a fringe of stray single-pixel columns that were never part of it. Measured in the browser: X/Y move with the area preserved exactly (19200 → 19200 px), W/H land on the requested size to the pixel, and a 30° rotation widens the bounding box 80 → 98 px while preserving area (4800 → 4801).

### Select ▸ Modify

- **Border**, **Smooth**, **Expand** and **Contract**, alongside the existing Grow and Feather. All four are thresholds of ONE primitive — the **signed distance** to the selection boundary: expand is `d ≤ +r`, contract is `d ≤ −r`, border is `|d| ≤ r/2`. No repeated passes, no accumulated error, and a genuinely **round** kernel.
- Round matters. The existing Grow expands each rectangle independently, which is a correct *square* dilation (dilation distributes over union) but leaves square corners — and it cannot simply be inverted for Contract, because **erosion does not distribute over union**: shrinking each rect of a multi-rect selection is plainly wrong. Verified: expanding a square reaches r straight out from an edge but NOT r diagonally past a corner, which is exactly the difference between a round kernel and a square one.
- The distance transform is Felzenszwalb & Huttenlocher's exact algorithm (a lower envelope of parabolas, separable, O(n) per row and column). Exactness is the point: an approximate chamfer transform would make "expand by 10" mean something measurably different along the diagonals than along the axes. Checked against Euclidean truth on both.
- The field is computed on a one-pixel border of zeros so the **canvas edge counts as a boundary** — otherwise a selection covering the whole document has no outside anywhere, its interior distance is infinite, and Select All → Contract does nothing at all.
- **Smooth blurs then re-thresholds**, so it rounds off corners and speckle while leaving the selection HARD. Feather is the control for softness; conflating the two would leave no way to tidy a jagged edge without also blurring it.
- Because the morphology runs on a raster, the result comes back as axis-aligned rects with any selection rotation already baked in — so the new selection is committed at angle 0 rather than being rotated a second time. Pure math in [select-modify.ts](app/lib/select-modify.ts) (30 Node checks); the browser results agree with it to the pixel (expand 28248, contract 12144, border 8896, smooth 19132 in both).

### Frames (placeholders)

- A **Frame** tool (`K`) draws rectangular or elliptical placeholders that **clip their contents**: paint or paste inside and it lands, stray outside and it is simply not there. **Layer ▸ Frame from layer** does the converse — wraps a picture you already have in a frame at its own content bounds, so nothing is cropped until you resize the frame.
- **A frame is not a new kind of clipping.** It is a layer carrying a `FrameSpec` plus a vector mask in the frame's shape, so the existing mask pipeline does the work — resolution-independent, already cached by path hash, already saved in the project file. The elliptical frame is four cubic anchors with the circle constant (measured mid-arc radius 50.0000 against a true 50).
- **Resizing a frame does not drag its content.** The content's offset is measured from the frame's centre, so growing the box would otherwise pull the picture along with it; the offset compensates, which is what makes a frame a window rather than a container.
- The fit model — **cover / contain / stretch / actual size**, plus the content's own offset and scale — is built and tested: cover always covers and contain always fits for every aspect ratio tried, scaling happens about the frame's centre so nudging then scaling does not also slide, and degenerate input (zero-size frame or image) returns finite numbers instead of spreading NaN.
- **Placing a picture in a frame:** drag an image file onto the canvas with a frame selected and it goes in, fitted by that frame's **Fit** setting (the options-bar control, which edits the selected frame rather than a tool default — fit is a property of the frame) and clipped by its mask, as one undo step that replaces whatever the frame held. **File ▸ Import** routes the same way, so a frame gets filled rather than covered over by a new layer; extra images in the same import still arrive as ordinary layers, so nothing is dropped. Measured: a 2:1 image into a 5:4 frame fills it **30576/30576 px on cover** and letterboxes to exactly **19600 px on contain**, with **0 px outside the frame** either way.
- **Canvas file drag-and-drop** exists because of this work — it never did before, though the README claimed it. With no frame selected a drop opens the ordinary import options, so a drop and File ▸ Import agree; `dragover` must `preventDefault` or the browser navigates away to the file and takes the document with it.
- **Re-fitting, at any time.** The placed picture is kept at its **natural size** in the engine, so changing Fit re-renders the frame's content immediately rather than governing only the next placement; a **Scale** slider and nudge arrows position it inside its window, and Reset recentres it. Quality does not degrade across repeated changes, because every render starts from the original rather than from the last fitted result — which would be a resample of a resample, and could never bring back what the previous fit cropped away.
- **Kept in the project file** (v23, `frameSource`), so re-fitting still works after a reopen — the whole reason for storing it. The frame layer's own pixels still carry the fitted result, so a file opened by an older build looks right; it simply cannot re-fit. Sources cost roughly one extra copy of each placed image, which is what a re-editable placement costs anywhere.
- **A bug this uncovered:** the project loader rebuilt each layer field by field and never carried `frame`, so a saved frame reopened as an ordinary masked layer. It still clipped — which is why nobody noticed — but it was no longer a frame: no Fit, no placement target, nothing to re-fit. Present since frames shipped; `sanitizeFrame` had existed for exactly this and was never wired up.
- 51 Node checks ([frame.ts](app/lib/frame.ts)), 9 in the browser for the clipping and 13 for placement.
- **Not yet**: placing an image *into* a frame through import or drag-drop — the fit maths above is what that will use, but `importAsLayers` still needs a branch for "the active layer is a frame". Until then a frame is filled by painting or pasting into it, which the clipping already handles.

### Direct selection (path editing)

- A first-class **Direct selection** tool (`A`) for reshaping a path after it exists: click an anchor to grab it, **Shift-click** to add to the selection, **marquee-drag** to take several, then drag them together. Handles appear on selected anchors and pull the curve; **Alt** while dragging a handle breaks the symmetry. **Alt-click an anchor** flips it between corner and smooth, **Alt-click a segment** inserts a point there, **Delete** removes the selected ones.
- **A separate tool, not more Pen.** The pen's primary click means "add a point at the end of the path"; direct selection's means "grab whatever is under the cursor". Those cannot both be the primary action on one tool, which is why Illustrator splits them and why this does too. It shares the Pen's live path and overlay, so there is one skeleton renderer and one engine session rather than two.
- **Inserting a point does not move the curve.** Splitting a cubic at *t* with de Casteljau yields two cubics whose union is exactly the original — every new control point is a convex combination of the old four. Measured worst deviation **4e-14px**; the obvious alternative (drop an anchor on the curve with retracted handles) deviates **2.9px** on the same test curve, which is what that number is there to contrast with.
- **Smooth means collinear.** Dragging one handle of a smooth anchor swings the opposite one to stay opposite *while keeping its own length* — a mirror that also resized the other side would quietly undo shaping you had already done. Dragging a corner's handle leaves its partner alone.
- **Editing writes BACK to the stored path.** The Paths panel's **Edit** used to load a path into the Pen, where committing produced a *new* Work Path and left the original untouched — the "editing after commit is limited" gap. Edit now opens the path in Direct selection and the commit replaces that path. Verified in the browser: after an edit the panel still holds exactly one path, and filling it produces the edited geometry.
- A path is never reduced below two anchors, and the source array is never mutated — every operation returns a new one, so undo and the live preview cannot alias each other.
- 67 Node checks ([path-edit.ts](app/lib/path-edit.ts)), 12 in the browser. Measured end to end by filling the path onto a layer: dragging the apex of a triangle down took its height 148 → 203px with the top edge unmoved, and Alt-inserting a point on the top edge then raising it took the top 76 → 26px with the rest of the path unchanged.

### Custom shapes & SVG import

- A **Custom** kind on the Shape tool with a library of outlines (arrow, star, heart, check, cross, speech bubble, lightning, moon), plus **Import SVG…** to add your own and **Export** to a `.gshape` file. A preset is nothing but a name and a path normalized into the unit square, so drawing one is "scale this path into the drag box" — which is what lets an imported logo behave exactly like the built-in rectangle: same fill, same inside stroke, same live resize, no second code path.
- **A complete SVG path-data parser** ([svgpath.ts](app/lib/svgpath.ts)) reduces everything a `d` string can say to four absolute commands — move, line, cubic, close. Elliptical arcs become cubics (endpoint → centre parameterisation, split at 90° so a cubic can follow the ellipse: measured worst deviation **0.0014px** from a true circle), quadratics become cubics, H/V/S/T are expanded, relative commands made absolute.
- **Parsing is deliberately lenient**, because real files are. Commas and minus signs as separators, exponents, implicit command repeats, extra coordinate pairs after a move (which are lines, not moves). The one that is not just leniency: **arc flags run together** — `a5 5 0 011 1` is `(5,5,0, flag 0, flag 1, 1,1)`, and reading it as a plain number list gives `(5,5,0,11,1)`, two arguments short, so the arc is silently dropped. Every minifier writes them that way, so a plain number scan loses most of the curves in a minified file. Arcs get their own flag-aware scanner.
- **Bounds solve the cubic extremes** rather than sampling or using endpoints. A curve that bulges past its endpoints would otherwise be reported as flat and squashed when fitted — checked with a curve whose true height is 7.5 and whose endpoints alone give 0.
- **Normalizing preserves aspect** and centres the short axis. Stretching each axis to fill the unit square is the obvious alternative and would turn every stored shape into a square, so a heart would only look right in a square box.
- **Import is not an SVG renderer** and says so: it extracts geometry (`<path>` plus rect / circle / ellipse / polygon / polyline / line) and drops paint, text, gradients, filters and transforms. All elements combine into ONE shape, since an icon is normally a body plus holes and splitting them yields fragments that mean nothing alone. Even-odd filling keeps the holes: verified by importing a ring and measuring **alpha 0 at its centre with alpha 255 on the ring**.
- Custom shapes get an **inside stroke** like the others, but by clipping to the path and stroking at double width — the inset-ring construction the rectangle and polygons use only works for convex shapes.
- The resolved path travels on the layer's geometry rather than a preset id, so a document keeps its shape after the preset is renamed or deleted.
- 54 Node checks on the parser, 60 on the library, 18 in the browser (a rectangle fills 99.7% of its box, the star 33.9% — that ratio is what separates "drew the shape" from "drew a box the shape's size").

### Brush texture & dual tip

- A **Tip shape** popover in the brush options bar, applying to the ordinary brush, the pencil and the eraser (everything on the baked-tip path). Both options multiply a dab's coverage — neither touches colour.
- **Texture** runs the stroke over one of five procedural surfaces (Canvas, Burlap, Grain, Speckle, Grid) with **Scale**, **Depth** and **Invert**. The patterns are functions rather than image assets: nothing to load, nothing to serialize beyond a name, and no pattern-picker to build — which is also the honest boundary, since a user-supplied pattern library is the separate feature that fill layers and pattern text fills are still waiting on.
- **The grain is anchored to the CANVAS, not the dab** — `texel(pattern, x, y, …)` is a function of document coordinates. That is the whole difference between a texture and a rubber stamp, and it is what the tests mostly check: painting the same line a second time leaves the pits exactly where they were (1231 empty px → 1231), and so does a pass at a different offset. Depth 0 is an exact bypass rather than a very faint texture.
- **Dual tip** scatters a smaller secondary tip inside the primary, eroding it into bristles. **One pattern is chosen per stroke**, not per dab: cycling per dab was the first attempt and consecutive dabs — overlapping ~90% at normal spacing — simply filled in each other's gaps, producing a stroke measured *pixel-identical* to an ordinary brush. Holding one pattern makes the gaps line up dab to dab, which is also what a real bristle brush does. Each new stroke picks a different one, so going over a stroke again fills in and builds up.
- The defaults are deliberately **sparse** (22% size, 120% scatter, 4 dabs). The first defaults — six dabs at 45% — overlapped into a near-solid disc, so switching the option on only made the stroke slightly narrower, which is indistinguishable from turning the size down. A Node check now asserts that even the fullest of the eight bristle patterns leaves real gaps.
- Texture is evaluated per dab at document coordinates rather than tiled into a repeating pattern (which would seam, the noise not being periodic) or baked into the tip (which would move the grain with the brush). The cost is only paid when the option is on.
- 51 Node checks ([brush-tip.ts](app/lib/brush-tip.ts)), 23 in the browser. Bristle *separation* is asserted exhaustively in Node over all eight patterns rather than in the browser, where the pattern is drawn at random per stroke and a single-band draw would make the test flaky.

### Frame tool: pointer, readout and rubber band

- Three defects, all in the plumbing every other rubber-band tool was already wired into.
- **No pointer.** `frame` was missing from the cursor chain and fell through to `default` — an arrow, which says nothing about where the corner will land. It now has a **custom** pointer rather than borrowing the generic crosshair: a crosshair with a frame glyph in the lower-right quadrant, built the way the eyedropper's is (a wide dark stroke under a thin white one, so it reads on any artwork), hotspot on the crosshair centre where the drag actually starts, and `, crosshair` after the data URL as the fallback. The corner marks are four brackets rather than a closed rectangle, because at 32 px a full outline turns into a grey smudge.
- **No size readout.** The live `W × H` the Info panel shows comes from `tickAnts`, which read `dragRectRef` (the marquee) and `moveRef` (a move) and nothing else. The Frame tool keeps its drag in `frameDragRef`, so it reported nothing at all.
- **The outline was erased in the frame it was drawn.** `frameDragRef` was missing from the overlay loop's keep-alive list, and that loop CLEARS the overlay when it stops — so every tick painted the rubber band and then wiped it. Measured at **0 px of overlay ink while actively dragging**, which is why this reads as "the Frame tool has no feedback" rather than as the subtle flicker the keep-alive list usually causes. It is the third time that list has been the culprit; the Move-tool transform box and this share a root cause.
- 13 browser checks. Each expectation is taken from the **Marquee** doing the same job in the same session rather than invented — same crosshair, same readout row, same outline-survives-a-pause — so the bar is "behaves like the tool next to it", and the reference legs would fail first if the harness itself drifted. Mutation-tested: reverting the cursor fails 5 checks, dropping the keep-alive 1, removing the readout 2, reporting width twice 1, and moving the cursor hotspot 1.

### Star shapes, and vertex dragging beyond the trapezoid

- A new **Star** shape kind with two on-canvas handles: the **inner** vertex sets the waist, the **outer** vertex sets the rotation. Both are polar drags about the box centre, which is what makes them read as one widget. Plus a **Points** slider (3–24) — and a waist pushed to 1 is a regular polygon, so hexagons and octagons fall out of the same kind rather than needing another.
- **The star had to become parametric to be draggable at all.** It shipped as one of the custom-shape presets: a fixed ten-point SVG path. There is no "inner corner" of an arbitrary path — nothing in the data says which vertex is which — so no amount of node plumbing could have reached it. `starPoints(box, {points, inner, angle})` replaces the preset with real geometry. The old preset stays in the library, so documents that used it are untouched.
- Inscribed in the box's **ellipse**, not its circle, so a star fills a wide box the way the triangle and trapezoid already fill theirs. The waist drag measures in the same elliptical units — the point 0.7 of the way out along the ellipse is 0.5 of the way out along the circle, so getting this wrong drifts the handle away from the pointer on any non-square star.
- The waist **snaps to the collinear ratio** — the proportion at which a star's spike edges run dead straight through, `cos(2π/n)/cos(π/n)`, which is 0.382 at five points and is what makes a pentagram look like a pentagram. It is offered only where it lands in (0,1); below five points the formula gives −1.
- **Non-convex, so the stroke is drawn differently from the other polygons.** The triangle and trapezoid stroke themselves as the ring between the outline and an inward offset — a construction only valid for CONVEX shapes, because offsetting a reflex vertex along its bisector turns the waist inside out. The star uses the clip-and-double-width technique the custom shapes already use. Corner radius is bounded by the shortest EDGE rather than by `polyInradius`, whose 2·area/perimeter is far larger than a spike can take.
- **Rectangles gained a corner-radius handle** on the top edge, snapping to square and to fully round. It writes to the same Radius the options bar holds — one number reached two ways, not a second setting.
- **Where nodes were NOT added, and why.** The ellipse is entirely determined by its box, so a node would have nothing to say. The remaining custom presets — arrow, heart, speech bubble, lightning — are fixed path data in the same position the star was in: each would need its own hand-authored parameters (a tail position, a head size) before anything could be dragged. The hit test, the overlay dots and the drag now all read one `shapeNodes()` list, so a node can never be drawn somewhere it cannot be grabbed.
- 21 Node checks ([shapes.ts](app/lib/shapes.ts)), 23 in the browser, all measured off pixels against closed-form predictions rather than recorded numbers: a star's area is `n·R·r·sin(π/n)`, so a default pentagram in a 400×400 box must cover 44903 px (measured 45479, 1.3% out) and the same star with its waist dragged to 0.7 must cover 82272 (measured 82813). Rotation is told from a resize by the ink count staying put while the widest row jumps from above the centre to below it.
- Mutation-tested: 12 breakages of the geometry, 11 caught with the control surviving; 6 of the wiring, all caught. Two things fell out of it. A `points < 5` guard on the collinear ratio proved **unreachable** — every count it rejected, the range check rejected too — so it went, on the same principle as any other branch that cannot be made to fail. And the elliptical-units mutant initially **survived**, because every browser check drew a square box, where circular and elliptical are the same number; a 400×200 leg now separates them (41602 px against a circular reading's 29389).
- One real bug found in the wiring: the live shape re-rendered on every setting except the new one, so the Points slider moved and nothing happened until the shape was redrawn. It was missing from the restyle effect's dependency list.

### Region-scoped effects recompute

- The settled pass after a stroke used to re-render a styled layer's effects across the **whole document**: 12 MP of `renderStyled` for a change covering a few thousand pixels. On 4000x3000 with one default drop shadow that was **289 ms of blocking per stroke** ([bench-bigdoc.js](tools/bench-bigdoc.js)). A miss on a cached styled product is now repaired in place — **median blocking 289 ms -> 0 ms**, with no task left long enough to drop a frame.
- **Two rects, and the difference between them is the whole correctness story.** OUT is the dirty rect grown by the effects' reach: output can only have changed that far from the pixels that changed, so everything outside it in the cached product is still valid and is kept. IN is OUT grown by the reach *again*, because computing OUT correctly needs every input pixel that can influence it. The border of the IN render is therefore wrong — it was computed without *its* neighbours — and is discarded; only OUT is blitted back.
- **The cached product is no longer thrown away on a bounded change.** `bumpPixel` used to `dropCache` unconditionally; it now keeps a region-patchable node's canvas and records what went stale, which is what leaves something to repair. Anything else — groups (their key folds in every child), fill layers, masked layers, smart-filter stacks — drops exactly as before.
- **A miss is only repaired when the key moved in one place.** `onlyPixelsChanged` compares the cached key against the new one field by field and demands that *only* the leaf pixel version differ. A change to the effects, the colour space, the mask or the document epoch changes the whole product and takes the full pass.
- **Position dependence is a separate gate from reach, and conflating them is the trap.** Reach answers "how far does a changed pixel spread?"; a gradient overlay and a gradient-filled stroke additionally take their geometry from the canvas they are handed (`cx = w/2`), so a sub-canvas silently moves and rescales them however much padding it gets. `effectsPositionDependent` keeps those on the full pass — and the rail proves it by asserting the region counter does **not** move for a gradient overlay while the pixels still match.
- **Byte-identity is necessary but not sufficient, and the rail says so.** It also holds when the region path never activates and everything quietly takes the full pass — which is exactly what happened the first time: all five effects came back "0 of 8294400 bytes differ" while the path had never run once. The engine now counts repaired misses (`regionHits`) and the pixels they touched, and [verify-region-scope.js](tools/verify-region-scope.js) asserts the counter moved. Two of my own test bugs surfaced that way: the per-effect section measured across the *first* stroke after enabling an effect (which has no cached product to repair), and it ran on a layer still carrying the blur and noise filters from an earlier section, which `regionPatchable` correctly refuses.
- 41 Node checks ([reach.ts](app/lib/reach.ts), previously untested despite being the correctness contract) and 23 in the browser. The Node suite is written from one asymmetry: an under-estimated reach is a seam at the border of the repaint, an over-estimate only costs efficiency — so it pins every filter's radius, asserts reach never shrinks as a parameter grows, that fractional radii round *up*, and that an **unknown filter type refuses to be region-scoped** rather than being assumed safe.
- The browser rail proves each effect's reach empirically rather than by reading the code: Outer Glow, Inner Shadow, Inner Glow, Bevel & Emboss and Stroke each get their own stroke and must come back byte-identical **and** have taken the region path. Measured activation on a 12 MP document: one repaint touching **166,306 px — 1.39%** of a full pass.
- **Masked layers came next, and were nearly free.** Both mask kinds multiply the styled render per-pixel, so they reach nothing: the repaint re-applies them over exactly the rect it just painted, clipped so nothing outside is touched. A masked, shadowed layer went **280 ms -> 0 ms** on the same 12 MP document. It earns its own rail leg because the cached product is styled-THEN-masked — repainting the styled pixels without re-masking would punch the mask's hole open again *inside* the rect, and only a byte diff would notice.
- **Finding the masked case at all took fixing the measurement twice.** The first bench reported no change and `regionHits 0`: adding a mask selects it for painting, so the stroke was landing on the MASK (a different path that drops the cache rather than marking it stale). The fix was to click the layer's image thumbnail — which is a `<span>`, not the canvas the first selector looked for, so the second attempt found zero elements and timed out rather than silently measuring the wrong thing.
- Scope, stated plainly: this covers a **leaf layer carrying effects, with or without a mask**. Groups, fill layers and smart-filter stacks still take the full pass — refused by one predicate rather than half-handled, which is why the whole thing stays byte-identical.
- **The smart-filter half of the original item turned out to be already solved, and not where the time is.** Measured on a 12 MP document with a blur smart filter: a stroke blocks **1169 ms**, and 100% of it is the *live* draft frames (100 frames over 5 strokes x 58.6 ms = 1172 ms, which matches). The settled full-resolution pass does not block at all — `kickFilterJob` already hands it to a worker. Within a live frame the split is downscale 0.9 ms, `getImageData` 4.8 ms, **`applyFilter` 52.5 ms**, upscale 0.2 ms: the kernel on the 750k-pixel draft, not setup and not the cache. Region-scoping the cached recompute, as the item proposed, would therefore win ~5% of a case that is already off-thread. The promising direction was region-scoping the LIVE frame — filter the dirty rect at full resolution instead of the whole document at quarter resolution — which is the section below.

### Region-scoped LIVE filter frames

- **Why the live frame is a different problem from the settled one.** The settled pass is already off-thread: `kickFilterJob` posts it to a worker, keyed by the node's key. A live paint session has no such key — it mutates the layer's pixels without a version bump, on purpose, so nothing can describe the source — which is why the worker cannot serve it and every live frame ran the stack on the main thread. `renderFilteredDraft` coped by shrinking the work rather than the area: the whole document at quarter resolution, ~750k pixels a frame, which is both slow *and* a visible quality loss — you painted against a soft approximation of your own picture.
- **`liveFilterRegion` shrinks the AREA instead.** Once per stroke it copies the settled product out of `filteredCache`, then each frame re-filters only `padRect(dirty, stackReach)` at **full** resolution and patches it in — the same OUT/IN construction as the settled recompute, for the same reason. Measured on 4000x3000 with one gaussian blur and a 160 px brush, arms interleaved in one sitting ([bench-livefilter.js](tools/bench-livefilter.js)): **median blocking ~2.2 s -> 51-118 ms (95-98% less across two sittings; the machine itself ran twice as fast in one of them, which is why the arms are interleaved and the ratio is the number that travels)**, worst single task ~115 ms -> ~53 ms, **204k px filtered per frame against 750k** for a draft frame — and at full resolution, so the softness goes away as well as the stutter.
- **The seed is only sound because of what does *not* change during a stroke.** `pixelVersion` does not move until `endStroke` bakes the stroke, so the pre-stroke product's key IS the current key — which is exactly what makes a cached product safe to copy and patch. The guard demands that key, quality `"full"` (patching sharp full-res pixels into an upscaled half-res product would leave a seam around the stroke), and matching document dimensions; anything else declines to the draft.
- **The economics are against the DRAFT, not against a full pass.** `regionWorthIt` asks whether a region is a small share of the document, which is the wrong question here: at 60% of a 12 MP document it would happily accept a region twelve times the size of the draft it is replacing. The live gate compares `IN` against the draft's own pixel count instead. On a document small enough that `draftScale()` is already 1 the comparison is against the full canvas, so the region path takes over there too — which is what makes the correctness rail below possible.
- **`renderFiltered` and the region path now share one `filterStack`.** The premultiplied filter-mask interpolation is subtle enough that two copies would eventually disagree — there is already a third in `renderFilteredDraft`. The shared version takes explicit dimensions and lazily-supplied buffers, so it serves a whole document and a single region of one; the full-canvas path exercises it on every golden and pixel-identity run.
- **Choosing an oracle was most of the work.** Region-on against region-off on a large document compares a full-resolution region against a quarter-resolution draft: they differ *by design*, so nothing is proved. On an 800x600 document `draftScale()` is 1, which makes the off arm a real full-document, full-resolution `renderFiltered` — precisely what the region path claims to reproduce. [verify-region-scope.js](tools/verify-region-scope.js) §7 captures one **mid-stroke** frame per arm, without releasing the button, and undoes between them so both arms start from identical pixels.
- **The rail reports two numbers, because they answer two questions.** Inside a band along the stroke's centreline — pixels the region path itself rendered — it demands **zero** difference, and gets it across a plain blur, a filter at 70% opacity (which takes the blend branch, the one place a reused oversized scratch buffer could read back the wrong rect) and a **painted** filter mask. Everywhere else is the copied seed, reported separately.
- **The first version of that rail passed while proving nothing, and the reason is worth recording.** The gradient fill paints the layer in the FOREGROUND colour, so a brush stroke straight afterwards paints that same colour onto itself: the stroke changed a few thousand antialiased edge bytes, and a blur smoothed even those below one LSB. Both arms were byte-identical because **both were identical to the pre-stroke image** — the stroke was invisible. The `]` shortcut compounded it: it does not reach the engine from Playwright (24 px before and after 26 presses), so the harness's `bigBrush()` had always been inert. The rail now swaps foreground and background, sets Size through the options bar, and asserts that the band contains pixels the stroke actually repainted — 4,992 bytes of them — before believing any "identical".
- **A pre-existing defect fell out of it: the smart-filter worker and the inline path disagree by 1.** With no live session in play at all, a settled composite computed by the worker differs from the same one computed by `renderFiltered`: on 800x600 with one blur at 70% opacity, 480,000 of 1,920,000 bytes — exactly one byte per pixel, the **red** channel, every one of them **-1**. At 100% / Normal they agree exactly, which localises it to the blend branch, where the worker composites on an `OffscreenCanvas` and the engine on an `HTMLCanvasElement`. No rail had ever used a filter with a non-default blend or opacity, which is why it survived. It is reported and bounded rather than folded into the region check — blaming the region path for it would either mask a real bug or fail for something it never touched — and it is now its own TODO item.
- Scope, stated plainly: this covers a **brush stroke on a leaf layer** whose filter stack has a finite reach. A **mask** stroke declines (it leaves the layer's pixels alone, so the filter's input never changes — the draft frames it still runs are pure waste, and a separate win). **Groups** decline, as they do for the settled path. Every non-paint live session declines because only a stroke tracks a dirty rect — a selection *move* on a filtered layer still costs 166 ms in [perf-suite.js](tools/perf-suite.js), which is the obvious next slice.

### Projects reopen in the colour space they were written in

- **The bug took five attempts to reproduce, and the first four were all byte-identical.** Ordinary save/open in the same session; after a page reload; in a brand-new browser context with no localStorage or IndexedDB at all; with Display P3 persisted on both sides; and through the entire crash-recovery zip. Every one came back exactly as written. The condition none of them had is the one that matters: **the working space at OPEN time differing from the space at SAVE time**. Saved in P3, opened in a session defaulting to sRGB: **27,550 of 120,000 bytes differ, and 0 of them are alpha** — the reported symptom precisely.
- **The reload in the original report was incidental.** It was never about reloading: a reload merely happens to be one way the persisted preference stops applying (a different browser, a cleared site data, another machine would all do it). That is worth recording because the report's own framing sent the first four attempts down the wrong road.
- **Cause.** Layer pixels are stored as PNG data URLs, and a canvas in a wide-gamut space writes them with that profile attached. The project file recorded **no colour space whatsoever**, so on decode the browser did exactly what it is supposed to do: colour-manage the artwork into whatever space the destination canvas was in. RGB shifts, alpha does not — which is what made it read as a rendering quirk rather than a lossy reopen.
- **Fix**: `workingSpace` in the project file (v24), and the loader adopts it *before* anything decodes. Both the space change and the pending pixel load land in one React update, and CanvasArea's colour-space effect is declared above its pending-load effect, so the engine has already switched when the images arrive.
- **Adopted with `setColorSpaceState`, deliberately not `setWorkingSpace`.** Opening a file is not the user choosing a preference, so the persisted one is left alone and their own space returns next time the app loads. A toast says which space the file brought with it, because silently changing a global setting is worse than saying so.
- **It ran in both directions.** An sRGB project opened while working in P3 was equally wrong (29,264 bytes) — not merely "wide-gamut files degrade". The rail covers P3→sRGB, sRGB→P3 and the emulated Adobe RGB, whose bytes stay on an sRGB canvas but which still has to be recorded so the adjustment maths comes back the same.
- [verify-colorspace-roundtrip.js](tools/verify-colorspace-roundtrip.js), in CI: each leg authors in one space and opens in a **brand-new browser context** primed to a different one, so what comes back can only have come from the file. Every leg asserts the opening session genuinely started in the other space before the file was opened — byte-identity would hold trivially if the two were secretly the same. Mutation-tested by removing the adopt: 6 of its 12 checks fail, in all three directions.
- **A gap this exposed in an existing rail:** the smoke test's crash-recovery leg compares recovered documents by **ink count** — an opaque-pixel total, which is exactly the half of this symptom that does not change. A pure colour shift passes it. Logged as its own TODO item rather than quietly widened here.

### Clearing the lint warnings — and the bug one of them was pointing at

- **Zero problems, and the gate tightened to match.** `npm run lint` is now `eslint --max-warnings 0`, so CI fails on a warning as well as an error. That is only worth doing once the count is actually zero: a gate that is red on arrival is a gate everybody learns to ignore, which is why it landed one step after the errors rather than with them.
- **Eight unused bindings were dead and went** — each grepped for other uses first rather than trusted to the linter, since a value import can be used in a type position. One was a loop counter (`p` in the HDR tone pass) that was incremented and never read.
- **The ninth was deliberate, and the config was wrong.** `{ maxSize: _unused, ...rest }` is the idiomatic way to STRIP a key, and the named sibling is unused by construction — `ignoreRestSiblings` exists precisely for it and is typescript-eslint's own default, which the Next preset leaves off. Restoring that option (plus the conventional `^_` patterns for arguments a signature requires but a body does not use) is a fix to the configuration, not a silencing of the code.
- **The two `exhaustive-deps` warnings were hiding a genuine, user-visible bug**, which is exactly why the TODO said to check them rather than blindly add the deps. `drawAnts` is `useCallback(..., [])` **on purpose** — it is the overlay's per-frame draw and must not be rebuilt — and everything changing inside it goes through a ref. Except one line: the frame-chrome branch read the `activeLayerId` **prop**, which an empty dependency list captures at mount and never updates. So the dashed guide around a selected **frame layer** was drawn for whatever had been selected when the canvas mounted — in practice, a frame drawn afterwards got no outline at all.
- **Measuring it took two attempts, and the first proved nothing.** The overlay loop stops and clears itself when nothing needs it, so parking the pointer away from the canvas leaves the overlay blank whether the bug is present or not — the first probe dutifully reported "no chrome" for a reason that had nothing to do with the bug. Holding the loop open with an eyedropper hover (one of its keep-alive branches, and one that draws almost nothing itself) made the comparison real: **16 px of overlay ink → 3,224** with the frame selected, and still 16 with a plain layer selected. The fix is one line — `activeLayerIdRef.current`, the pattern the rest of the function already used.
- **The other two flagged dependencies were genuinely stable, and are now listed rather than suppressed.** `engine` comes from a ref initialised once; `transformBox` was a plain function rebuilt every render, so adding it would have rebuilt the entire overlay draw sixty times a second — it became a no-dependency `useCallback` (it reads only refs) first, which it needed to be anyway once `drawAnts` depended on it. Its engine access had to move to `engineRef.current`, because the `engine` const is declared far below and naming it in a dependency array up there would be a temporal-dead-zone reference.
- **Both accessibility warnings were real gaps, and adding the missing attribute was not the fix.** The colour picker's hue strip, opacity strip and saturation/brightness square all carry `role="slider"` and `tabIndex={0}` — reachable by Tab, and then completely inert, with no key handler at all. They now take arrow keys (Shift for ×10 steps; hue wraps around the wheel rather than clamping at 0 and 360) and report `aria-valuenow/valuemin/valuemax` plus an `aria-valuetext` that names both axes for the square. The command palette's `combobox` was missing `aria-controls` and `aria-activedescendant`: focus never leaves the input, so arrowing through the results announced nothing whatsoever.

### Clearing the lint errors, and what they were hiding

- **From 16 errors to 0, so `npm run lint` can gate CI** — it now runs in the `check` job ahead of the typecheck. Warnings are deliberately not gated: `eslint` exits 0 on them, so the remaining 13 stay visible in the log without blocking.
- **Five `prefer-const` went with `--fix`, which needed sweeping up after.** The same run also deleted nine stale `eslint-disable` directives — correct, but it removed the comment text and left whitespace-only lines behind. Cleaning those meant minding that this tree has both CRLF and LF files: the first pass silently missed `PreferencesDialog.tsx` because the regex assumed LF.
- **One `no-this-alias` was a design smell worth removing.** `evictOverBudget` held `const self = this` purely because a nested `function*` binds its own `this`. It is now a generator METHOD, `evictionCandidates()`, which keeps the laziness and drops the alias.
- **Seven prop→state mirrors moved out of effects, and that is a real improvement.** `useEffect(() => setDraft(value), [value])` renders the stale value, paints, and only then corrects it. React's documented pattern is to adjust DURING render — compare against a remembered previous value and set both — which re-renders before the browser sees anything. Applied to the numeric controls, the properties and metadata rename drafts, the command palette's highlight, the levels dialog's pick highlight, and the two popovers' position resets.
- **One ref write during render became `useImperativeHandle`.** RightDock published its layout handle by assigning `dockRef.current` mid-render, which is unsafe under concurrent rendering. Every call site in Editor.tsx goes through `dockRef.current?.` from a menu handler, never during render, so publishing it in the commit phase changes nothing about availability.
- **Four were suppressed with a written reason, and that was the right answer.** Three are `localStorage` reads after mount — moving them into render would cause exactly the hydration mismatch they exist to avoid, since the loaders return empty on the server. The fourth is measure-then-position: `getBoundingClientRect` needs a laid-out element, so it genuinely cannot happen during render. Notably `Tooltip.tsx` does the identical thing and the rule does *not* flag it, so contorting `GradientControl` into a shape the linter prefers would have bought nothing a reader would thank you for.
- **Two traps, both of which cost a cycle.** The React Compiler rules **stop analysing a component after the first error**, so fixing one reveals the next — RightDock's `set-state-in-effect` only appeared once the ref-during-render error was gone, and the error count moved 16 → 11 → 5 → 4 → 2 → 0 rather than straight down. And `eslint-disable-next-line` has to sit immediately before the reported `setState` line, not before the `useEffect` that contains it; placed on the effect it reports as an *unused directive* while the error stays.
- **Verified in the browser, because these rewrites fail in ways a unit test cannot see.** Get the comparison in a render-time adjust wrong and the component either stops re-syncing (a stale draft) or sets state on every render — "Too many re-renders", a blank screen. [verify-react-state.js](tools/verify-react-state.js) drives all eight components (10 checks, in CI): a numeric field re-syncing from an outside change, the name field following the selected layer, the palette highlight resetting, a tooltip appearing and being positioned and dismissed, the gradient popover opening on screen, and Reset Workspace reaching the dock through its new imperative handle (16 panels → 15 closed → 16 restored). The last assertion is the one that matters most: no React error reached the console during any of it.

### Continuous integration

- **Two jobs, split by what they need rather than by what they check.** [ci.yml](.github/workflows/ci.yml)'s `check` job runs `npm run check` (tsc plus 654 unit tests) and a production build with no browser at all, so a type error or a broken unit test reports in under a minute; `browser` boots the app and runs the five browser rails — smoke, pixel identity, golden effects, region scoping, worker/inline blend — as separate steps, so the run summary names which one broke instead of one opaque red X.
- **The premise needed checking, and half of it was wrong.** The TODO claimed every harness was already CI-ready. Exit codes and the declared `playwright-core` devDependency were fine, but `--url` existed in only **4 of 17** tools, and **all 17** hardcoded `channel: "msedge"` — a browser chosen because it happened to be on the machine they were written on. [launch.js](tools/lib/launch.js) now owns the launch for every tool, taking the channel from `--channel`/`$GQ_CHANNEL` and the URL from `--url`/`$GQ_URL`, still defaulting to msedge and localhost:3000 so nothing changes locally.
- **The channel change was verified, not assumed.** `golden-effects` compares an exact hash against a checked-in baseline, so running CI on a different browser than the one that recorded it is a real risk. Measured first: the hashes are **identical on Chrome and Edge**, for all ten effects. Pixel identity and smoke pass on Chrome too. Only then was the CI channel pinned.
- **Each rail is proved to honour `--url` rather than assumed to.** A tool that ignored the flag would quietly connect to whatever was on the default port and pass — the same vacuity trap as a byte-identity check that never ran. So all five were run against a port with nothing listening, and all five exit non-zero. `npm run <rail> -- --url ...` was then rehearsed verbatim against a live server, with `GQ_CHANNEL=chrome`, before the workflow was written around it.
- **CI has to use the DEV server, and that is not a shortcut.** The harnesses drive the app through dev-only console hooks — `__gqRenderCache` (pixel identity toggles the render cache to force the always-correct uncached path) and `__gqCrash` (smoke simulates a crash to test recovery) — and CanvasArea returns early from installing them when `NODE_ENV` is production. Against `next start` every browser harness would fail on a missing hook. The production build is still compiled, by the `check` job, so a build-only break is caught.
- **What is deliberately NOT in CI, and why.** The perf suite and the benches: they measure wall-clock, and a shared runner varies by more than the thing being measured — the perf suite already prints a calibration warning when the machine is off baseline, and on a runner it always would be. And `npm run lint`, which reports 16 pre-existing errors: wiring it in before those are cleared would make the build red from its first run and stay red, which only teaches everyone to ignore a failing build. Both exclusions are written into the workflow itself, next to the thing they explain.
- Two smaller things found on the way: `npm ci` was checked against the lockfile rather than assumed (it passes, and the lockfile's recorded version had drifted 14 releases behind `package.json` — resynced by hand, so no dependency resolution ran), and Next 16 refuses to start a second dev server while one is running, which blocks a second-port rehearsal locally but cannot happen on a fresh runner.

### Exact blending for the smart-filter stack

- **Two paths that were supposed to be interchangeable were not.** Handing the settled filter pass to a worker is only sound if the worker's product equals the inline one, and nothing checked that until a live region frame seeded from a cached product and inherited a discrepancy: on an 800x600 document with one blur at 70% opacity they differed on 480,000 of 1,920,000 bytes.
- **The stated cause was wrong, and measuring is what corrected it.** The obvious suspect — the worker composites on an `OffscreenCanvas`, the engine on an `HTMLCanvasElement` — was written into the TODO as fact, then **disproved**: a probe blending a 256x256 gradient through both surfaces (and through a worker) found them byte-identical in every combination, and `willReadFrequently` on either buffer made no difference either. What separates them is the DEGENERATE case. Blending a colour over *itself* must return that colour, and at 70%: **HTMLCanvasElement breaks on 8 of 256 values, rounding down; OffscreenCanvas breaks on 48 of 256, rounding up** — main thread and worker alike. The first probe had used a gradient where backdrop and source differed, which is exactly where the two agree.
- **So neither path was right, and matching them was the wrong goal.** The user-visible defect was not "cached and uncached disagree" but "a filter at partial opacity shifts flat colours by a level even where the filter changes nothing". Picking one rasteriser would have kept that. [blend.ts](app/lib/blend.ts) computes the blend in exact arithmetic instead — W3C Compositing and Blending Level 1: the blend function per mode, then simple alpha compositing of the blended source — and both the engine and [filters.worker.ts](app/workers/filters.worker.ts) call it. Neither touches a canvas to blend any more.
- **Keyed on the canvas OP, not the blend-mode name.** `BLEND_MAP` maps Dissolve onto source-over and Linear Burn onto multiply as documented approximations. Keying the new code on the op it produces means those approximations are preserved exactly rather than quietly becoming their true formulas — this change was meant to fix a rounding disagreement, not to redefine two modes.
- **What it costs, measured rather than assumed.** Removing a `putImageData` → `drawImage` → `getImageData` round trip sounds like a speed-up; it is not, because that round trip is a GPU blit. Back to back on a 4000x3000 document with one blurred filter at 70%: the canvas blend **122 ms**, exact **186 ms**. That is the price of correctness, and it falls on the inline path only — the settled pass runs in the worker, and a live stroke now blends over its dirty region rather than the whole document. A first draft cost **367 ms**, and almost all of the difference was switching on the op string inside the pixel loop instead of picking the blend function once; the non-separable modes also allocate no per-pixel triple.
- 70 Node checks across two files. The property suite leads with the one both rasterisers failed — every value at every opacity, blended over itself, must come back unchanged — then pins each separable mode against its spec formula on a sampled 8-bit grid, the compositing endpoints (alpha 0 and 1, transparent source, transparent backdrop, where multiply must NOT darken), `lighter` as Porter-Duff plus rather than a blend function, and the aliasing rule the filter stack relies on.
- **One test was wrong before the code was.** The identity check originally asserted that a *translucent* colour over itself returns the same alpha. It does not, and should not: source-over accumulates coverage, so `ao = as + ab(1 − as)` is legitimately larger. The assertion now states the colour identity and the alpha formula separately, which is the property that was actually meant.
- **A captured-canvas fixture as a structural check.** Rounding disagreement is one or two levels; swapped operands or a mistranscribed formula is tens. Every op is held to Δ2 against a checked-in grid captured from a real Chromium canvas — and that bound is the MEASURED maximum (source-over, exclusion, difference and hard-light at 0.7 reach exactly 2; everything else is 0 or 1), not a comfortable margin.
- [verify-worker-blend.js](tools/verify-worker-blend.js) holds the worker's product and the inline one to byte-identity across ten blend modes through a new engine hook that diffs the two PRODUCTS rather than whole composites — the earlier composite-level diff dragged in every group merge and layer blend on the way to the canvas and could not localise anything. It asserts the product's digest MOVES on each mode change, so "they agree" can never mean "nothing happened", and the hook reports "not ready" while a worker job is in flight rather than comparing against a stale product.

### The selection boundary trace, and the wand flood

- Both halves of a magic-wand click, profiled first. On a flood-filled 1920x1080 document a plain click cost **81.2 ms**, split `getImageData` 6.9 / flood **43.6** / rect decomposition 5.1 / boundary trace **28.6** — so the two named in the TODO really were 86% of it. (The TODO called the retrace "the part that actually costs"; it is the smaller of the two. The flood is bigger.)
- **The trace stopped looking at pixels.** It walked every cell of the region's bounding box twice — once for horizontal edges, once for vertical — which is the wrong shape of work, because a flood selection is mostly SOLID and almost every row is identical to the one above it. [mask-trace.ts](app/lib/mask-trace.ts) rebuilds it on RUNS: horizontal edges are the interval XOR of two adjacent rows' run lists, vertical edges are the run endpoints kept open across rows. A row identical to the one above now costs one comparison per run and emits nothing. **28.8 ms -> 3.1 ms** at 1920x1080, and the rect decomposition fell 4.2 -> 2.6 ms on the same idea.
- The vertical pass was written twice. The first version still swept the full column span per row — O(area) again, defeating the point — and only the second, which merges each row's run endpoints against the previous row's, is O(runs). Worth recording because the bug was invisible: it was correct, it passed every test, and it was fast enough to look like the win.
- **The flood fills rows, not pixels.** The old one walked cell by cell with a parallel `seen` map and paid a modulo AND a divide per pixel purely to recover (x, y) from a packed index. The scanline version fills a whole horizontal run per pop and seeds only the runs above and below, so the index maths is gone and `mask` is its own visited map. **43.6 -> 36 ms** — a real but modest 1.18x, because the old loop already tested each pixel exactly once and the scanline tests span edges two or three times; what it actually bought was the bookkeeping, not the test count.
- Seeds are packed one-per-int (`x | y << 16`), which keeps the stack at n ints instead of 2n and, with `seen` gone, leaves the wand's scratch **smaller than before** (4n bytes against 5n). Packing measured 43.8 ms on its first run and looked like a regression; three more runs put it at 35.6-38.4, indistinguishable from unpacked. One sample was not a measurement.
- **Same-machine A/B on [bench-selection.js](tools/bench-selection.js)** — 10 plain wand clicks 1032-1067 ms -> **832-840 ms** blocking, 10 add-clicks 1142-1194 ms -> **555-614 ms**, worst task 144 -> 88 ms. Add-clicks gain most because `combineSelection` re-traces the union box on every call. The harness header now warns that its absolute numbers do not travel: the same build measured 167 ms and 835 ms for the same scenario within an hour as the machine warmed up, which is exactly the calibration trap [bench-track.js](tools/bench-track.js) exists to avoid.
- **Verified two ways, because the two halves need different proofs.** The trace and the rect decomposition are checked in Node against the implementation they replaced, used as an oracle: 13 hand-built shapes (disc, ring, checkerboard, comb, staircase, single cell, one-pixel row and column), 200 random masks across the whole density range, and 100 random SUB-windows. Comparison is by unit-edge set rather than by segment list, so a different-but-equivalent merge passes and a wrong boundary cannot. The flood has no Node oracle — the colour match is inlined inside `magicWand` — so it is checked end to end instead: [ab-wand.js](tools/ab-wand.js) fills the selection and fingerprints the filled pixels, and all four scenarios (large flood, blob flood, tolerance 80, non-contiguous) came back **identical to the pixel** — 1959528, 38024, 2035576 and 2073600.
- One test earns its place alone: *emits no more segments than the oracle*. Edge-set equivalence would happily accept emitting every unit edge separately, which would make the ants far more expensive to draw — and the mutation that stops vertical runs merging is caught by that test and no other.
- 24 Node checks. Mutation-tested with 8 deliberate breakages (run off-by-ones in both directions, no horizontal edges, unmerged vertical runs, swapped open/close, rects that never extend downward, rects paired on their start only, a dropped trailing row) — all 8 caught, control untouched.
- A precondition is now written down where it is relied on: the bounds handed to the trace must CONTAIN the region, because cells outside are treated as empty so the boundary closes. The old code read across the box border instead, which differs only for a box that clips through set cells — something no caller does, and which would ask for an open boundary the ants cannot draw.

### Coalescing the shape-node drags

- The trapezoid's two side nodes and the triangle's apex rebuilt the live shape on **every pointermove** — `engine.liveShape` re-runs the geometry, the fill, the stroke and a composite. A high-rate mouse delivers several moves per displayed frame, so all but the last rebuild was drawn and discarded before anything reached the screen. Now one rebuild per frame, reading the node position at **frame time** — coalescing is only correct if the frame uses the newest input, which is why the handler writes `trapRef`/`triApexRef` and the frame reads them, rather than using the value the callback closed over. Same treatment the triangle-apex slider already had.
- **37.2 ms → 2.8 ms** of blocking for a 60-event burst (0.62 → 0.05 ms per event), with the frame count over the run unchanged (161 vs 157).
- **Measuring this at all needed bursty input.** Playwright's `mouse.move` awaits, so a scripted drag arrives at roughly one event per frame and shows *no difference whatsoever* whether the work is coalesced or not — the trap the apex slider's own comment records. The burst is therefore dispatched from inside the page, synchronously, with no await between events: what a 1000 Hz mouse does to a 60 Hz display.
- `ensureAnts` is deliberately left uncoalesced alongside it — it is already a one-rAF-at-a-time scheduler, so calling it per event costs a null check and keeps the node dots and snap guides exactly as responsive.
- **A flush-on-release was written, could not be shown to do anything, and was deleted.** The obvious worry is that the last moves of a drag never get their frame. They do: pointer-up does not cancel the pending frame, so it fires a moment later against the newest refs, and `engine.endShape()` is driven from a React effect, which runs after paint and therefore after that frame. Mutating the flush away failed *zero* checks even after a test was added that releases and commits in the same task with no frame available. A guard that cannot be made to fail is worse than no guard, so the code went and the reasoning stayed as a comment — "shouldn't this flush?" is the obvious question to ask of it later.
- 13 browser checks. The load-bearing one compares a bursty drag against a slow one **to the pixel** (both 263 px at x=338), because "it got faster" and "it still ends up in the right place" are different claims. Mutation-tested: freezing the value the frame closes over — the exact way a coalescing change goes subtly wrong — fails 5 checks, and skipping the mid-drag rebuild entirely fails 2. That second mutant is why a **mid-drag** sample exists at all: every other check reads the canvas after release, so a change that rendered only on release would have passed all of them.

### The layer-effects scratch buffer

- `alphaMask` — the RGB=0, A=silhouette buffer every effect marries its colour to — used to allocate a fresh canvas **and** a fresh `ImageData` on each call, once per *enabled* effect. It now reuses one of each, keyed on document size. At 12 MP: **32.7 ms → 23.4 ms** per effect (1.40x), byte-for-byte identical. End to end on a 4000x3000 document carrying five effects, the blocking time per edit went **2544 ms → 2453 ms**.
- **The change the TODO asked for was measured and rejected.** The plan was to fold the whole of `tinted` into one `ImageData` write — resolve the colour once through a 1x1 canvas, skip the full-canvas fill, the second canvas and the `destination-in` entirely. It is 0.73x, i.e. **38% slower**: it trades two cheap *native* passes for three extra byte stores per pixel in JS. Writing the RGB in afterwards through a `Uint32Array` view instead lands at exactly 1.00x. The premise — that the fill and the composite were the cost — was simply wrong; the cost was the allocation, which is what the version that shipped removes.
- Five formulations were benched at 3 MP and 12 MP before choosing. Two of them are traps worth recording: rounding half-**up** through a u32 view is 1.35x but disagrees with the current output (29 px, worst 7), and reusing the tint *output* canvas as well is 1.65x at 3 MP yet **0.83x at 12 MP** — faster on the size nobody is waiting on and slower on the size they are.
- **Reuse buys speed with a hazard**, so the verification is aimed at it rather than at the happy path: [verify-tinted.js](tools/verify-tinted.js) runs consecutive *different* alpha fields through the shared buffer, then a strictly smaller field after a bigger one (the classic stale-pixel bug), then a size change and back again — 42 checks across three sizes, each compared byte-for-byte against a freshly allocated buffer, each with its own non-vacuity assertion that the field was actually populated and carried >300 distinct alpha values.
- **`alphaMask` now returns shared scratch, so its result must be consumed before the next call.** Every caller did already, except the Stroke effect, which built its `ringMask` at the top of a block and drew it a dozen lines later with gradient construction in between. That was safe on the day and one edit away from not being, so the call moved down to sit against its `drawImage`.
- **The A/B rail gained a second document size, because a single-size rail cannot see this bug class.** Removing the size re-key from the scratch — which hands the second document a mask of the first one's dimensions, stretched by `drawImage` — passes `tools/ab-effects.js` and all ten golden effects *perfectly* when only one size is ever rendered. With the second leg it is caught at once: 46887 non-empty px against the correct 27475. Confirmed by making exactly that mutation, and the stale-alpha mutation too (which the existing rail already caught: hash `5fae3d5` → `1e041605`, and 7 of 10 goldens).
- The four micro-optimisations that do NOT work are now recorded together in the code, with their numbers, so the next person does not re-derive them: dropping `willReadFrequently` (10 ms faster, 445 px vanish), the u32 truncating write (25% faster, disagrees on 498k of 1M samples), the single-`ImageData` rewrite, and reusing the output canvas.

### Move-tool transform controls

- Photoshop's **Show Transform Controls**, in the Move options bar: the active layer wears a live box with eight handles. Drag one to scale, drag just outside a corner to rotate, drag inside to move. The setting persists with the other tool options.
- **It is the existing transform session, not a second one.** The pixels are lifted with the same `beginFloatFromSelection` the marquee uses, over the layer's own bounds, and the existing `resizeRef` / `rotateRef` drive it from there — so the scaling maths, `setFloatDst` / `setFloatRotation`, the resample smoothing, the live preview and the undo entry are all code that already ran. This was the reason the item was deferred once: a decorative bounding box is the wrong half of the feature, and a *parallel* implementation would have been the wrong whole.
- **The only genuinely new behaviour is what happens on release.** A `layerBox` flag on the shared refs tells the commit paths to bake the pixels and stop — no selection is committed, because the gesture never made one. The box simply re-measures from the layer's new content bounds on the next frame. Rotation's "did anything change?" test had to move with it: the shared path compares against `before.angle`, which belongs to whatever selection happened to be up, so the Move path compares against the grab angle instead.
- **The shared preview refs had to be hidden from the ants.** `resizePreviewRef` and `rotatePreviewRef` are what the marching ants draw from; borrowing them for a layer box meant that a marquee left up elsewhere in the document was redrawn at the *layer's* bounds and spun with it — an outline claiming pixels it had nothing to do with. One `tfLive` flag in `drawAnts` keeps the two apart.
- **Shift constrains and Alt resizes about the centre** — new to the shared resize path, so selections gained them too. Scaling a *layer* without proportion lock visibly distorts artwork in a way that reshaping a marquee outline does not, which is what made this part of the feature rather than a separate one. Clamping to the canvas is deliberately skipped while constrained: pushing an edge back inside would change one side's length and so break the very ratio the user asked to hold.
- **The rotate zone is corners-only, at half the marquee's reach** (22 px, against `RING_OUTER`'s 44). The marquee's ring wraps the whole outline, which is free there because nothing competes for those pixels; on the Move tool that band lies over the neighbouring artwork, so a click meant to auto-select the layer next door would have spun this one instead.
- **`layerContentBounds` is now memoized** on `pixelVersion:docEpoch`. It reads the whole layer — 48 MB on a 12 MP document — and the box asks for it on every overlay frame; the key is the pair the render cache already uses, so a committed pixel write or a canvas resize invalidates it exactly. The bounds are also what decides whether handles appear at all: no layer, a locked or parametric one, or an empty one all get nothing, on the principle that a handle you cannot drag is a worse affordance than no handle.
- The overlay loop's keep-alive list had to learn about the box: that loop **clears the overlay when it stops**, so the first version drew the box and wiped it one frame later. Caught by measuring the overlay rather than by looking at it — the hover-cursor check passed the whole time, because hit-testing never depended on the drawing.
- 36 Node checks ([transform-box.ts](app/lib/transform-box.ts)), 24 in the browser. The browser suite measures **pixels, not the overlay**: a handle dragged 100 px leaves the artwork exactly 100 px wider with the far edge unmoved; a rotation is told apart from a scale by arithmetic — a 30° turn of a 160×120 rectangle predicts a 199×184 axis-aligned box (measured 198×184) while the opaque pixel count barely moves, because rotation preserves area and scaling does not.
- Mutation-tested on both sides. Six deliberate breakages of the wiring — decorative handles, a canvas-sized box, the marquee commit path, the overlay keep-alive, an ignored toggle, an unwired Shift — were each caught by the check that names them. Of fourteen on the maths, twelve were caught and two survived: one equivalent, and one a real weakness — the reach test compared against `MOVE_ROTATE_REACH` itself, so doubling the constant moved both sides of the assertion and passed. It is pinned in absolute coordinates now.

### On-canvas brush HUD (Alt + right-drag)

- Hold **Alt** and right-drag anywhere on the canvas: horizontal travel sets the brush **size**, vertical travel sets its **hardness**, and the tip previews under the pointer with both numbers in a chip beside it. Every ring-cursor tool takes it — brush, pencil, eraser, heal, clone, blur, smudge, mixer, dodge/burn, sponge, history brush, Quick Selection and Red Eye — reading and writing the same values the options-bar sliders hold. It is a tool OPTION, not an edit, so like dragging those sliders it adds no history step.
- **The preview is the real tip.** `hudAlphaAt` reproduces the profile `PaintEngine.buildSoftTip` bakes — solid core out to `hardness/100` of the radius, then a linear ramp to nothing — and the disc's alpha is that coverage times one constant, with nothing composited underneath. So the preview can be *measured* rather than merely looked at: the browser check reads the alpha profile off the overlay and off a dab actually painted at the same settings, and the two have to agree (worst sample mismatch 0.059 of full coverage).
- **A dark backing plate under the preview was the first attempt, and it was wrong** — not cosmetically, but because compositing the veil over 35% black rescales the ramp: a hardness-40 edge came back reading like hardness 70 (0.64 where the painted dab gives 0.33). The contrast comes from the colour instead (red, which carries over light and dark artwork alike, and is why Photoshop's HUD is red). Caught by the profile comparison above; it is the one check that could catch it.
- **Horizontal travel is divided by the zoom, vertical travel is not.** Size is a length, so one screen pixel of drag is one screen pixel of ring diameter at every zoom — the ring grows exactly under the pointer at 25% and at 800%. Hardness is a percentage with nothing on screen to stay in step with, so it takes a flat 200 px of travel for the full sweep. Measured in the browser at two zooms: 40 px → 92 px at scale 1.94 and 40 px → 73 px at scale 3.00, which is the same 100 px of on-screen growth both times.
- **The gesture has to CLAIM the event, and only its own.** Right-drag already paints with the secondary colour on the paint tools, so the HUD is checked before every tool branch in `onCanvasPointerDown`; a version that did not claim it would resize *and* lay down a stroke. Both halves are asserted: the HUD drag leaves the document byte-for-byte untouched, and a plain right-drag (no Alt) still paints its 11344 px. `onContextMenu` suppression was widened to match, or the browser menu would open mid-drag.
- The disc is anchored at the **press point**, not tracked to the pointer: the whole purpose is to judge the tip against the artwork under it, which is impossible if it is running away from you. The committed size/hardness are echoed back into the session so the preview draws the values that were actually stored, rather than re-deriving them a frame behind React.
- Hardness is offered only where there is a soft edge to set. The Pencil, Quick Selection and Red Eye have no Hardness slider, so the vertical axis is inert for them rather than writing a number nothing reads.
- 29 Node checks ([brush-hud.ts](app/lib/brush-hud.ts)), 17 in the browser. Mutation-tested: 12 deliberate breakages, 11 caught immediately and both controls left passing. The twelfth survived because it was **equivalent** — a `hardness >= 100` early-out that the `inner = h/100` arithmetic already produced — so the dead branch was removed rather than the test patched around it. Replacing it with a real defect (capping the core at 0.999 the way the soft-tip path does) then survived too, a genuine gap: the flat-disc test sampled only as far as 0.99 of the radius and could not see a hairline rim ramp. It now samples to 0.99999.

### Brush angle, roundness & scatter

- The remaining two tip dynamics, in the same **Tip shape** popover as Texture and Dual tip and on the same baked-tip path (brush, pencil, eraser). **Roundness** squashes the tip, **Angle** turns it, **Scatter** throws the dabs off the stroke line.
- **Roundness/angle is a change of METRIC, not a second tip builder.** `tipRadius(dx, dy, r, angle, roundness)` rotates the *point* into tip space and returns a normalized elliptical radius, so the hard tip keeps its membership test (`<= 1`) and the soft tip keeps its existing falloff profile — it just measures distance differently. A soft flat tip is therefore still soft, which a separate elliptical builder would have had to re-derive.
- **The measurement that proves it is directional, not merely narrower.** A 40 px tip at roundness 15 draws a horizontal stroke **6 px** thick and a vertical one **40 px** thick — the short axis lies across the stroke one way and the long axis the other. Set Angle to 90° and the two swap exactly (40 px / 6 px). A tip that had simply been scaled down would have measured 6 px both ways, and the round-tip control (40 px / 40 px) rules out the opposite mistake.
- **Scatter offsets are in the STROKE's frame, not the screen's.** `scatterOffsets` returns `{along, across}`, which `lineTo` rotates by the segment direction before stamping. "Across the stroke" therefore means across *that* stroke wherever it is heading, so a curve keeps a constant spray width instead of pinching where it happens to run diagonally. **Both axes** additionally jitters along the direction of travel, which is what breaks up the even bead spacing for spray and foliage.
- **Amount is a % of the tip DIAMETER AT THAT DAB**, resolved through `tipDiameter(p)`, so a pressure-tapered stroke scatters proportionally — the spray narrows with the brush rather than staying at its full-pressure width where the stroke has thinned away to nothing.
- One RNG is seeded **per stroke**, not per dab and not per document, so a stroke is internally coherent while no two strokes repeat: painting over the same path fills in and builds up instead of stamping the identical pattern. Measured — two identical drags laid down 33320 px and 33128 px of ink.
- Amount 0 is an exact bypass (the offsets are literally `{0, 0}`), and roundness is clamped to 1–100 rather than allowed to reach 0, which would collapse the tip to a line of no width. **Angle wraps rather than clamps** — 190° is a direction, not an out-of-range error, so it sanitizes to −170° and not to 180°.
- **What separates "scattered" from "just a fatter brush"** is not the width of the band — a wider solid stroke would pass that too — but the raggedness of the leading edge: the per-column top-of-ink has standard deviation **0.0 px** for a plain stroke and **4.3 px** for a scattered one, while the band grows 40 px → 136 px.
- 24 Node checks ([brush-tip.ts](app/lib/brush-tip.ts)), 12 in the browser. The Node suite pins the geometry against an oracle rather than against recorded numbers: rim points are generated at arbitrary angles and fed back through `tipRadius`, which has to return 1 for every one of them.

### Mixer brush

- A wet-paint brush: it carries a **reservoir** of colour, drags a tip-sized buffer of colour **picked up** from the canvas, and lays down a mixture of the two. **Wet** is how much it absorbs per dab, **Mix** the ratio of picked-up paint to reservoir paint in what goes down, **Load** how full the reservoir is, **Flow** the deposit rate. Five named combinations (Dry / Moist / Wet / Very wet / Very wet, heavy mix) sit above the sliders, because nobody sets Wet-Load-Mix by hand until they know what the four do.
- **The reservoir behaves like paint.** It is spent by depositing and topped up by whatever the tip picks up, so a dry brush fades out over roughly a brush-width of travel while a wet one keeps going indefinitely — it is living off the canvas. An empty *but wet* brush still paints, because what it picked up is what it is painting with.
- **Implemented as a generalization of Smudge, not a second engine.** Smudge IS a mixer with Mix at 100 and no reservoir (its Strength is `wet = 100 − strength`), so the two share one per-pixel kernel and all the scaffolding around it — working buffer, carried tip buffer, sample-all pickup, dirty-rect blitting, selection clipping, history. In smudge mode the mixer terms are inert by construction (`deposit = 1`, `blend = 0`), which is why smudge comes out unchanged; verified in the browser alongside the new tool.
- **Pickup averages PREMULTIPLIED colour.** Averaging straight RGB lets fully transparent pixels — whose stored RGB is usually black — vote on the result, so picking up next to an edge would drag a dark fringe into the brush. Checked directly: a half-transparent red region picks up as pure red (255), where straight averaging gives 127.5.
- **Clean / Load after each stroke resolve when the NEXT stroke begins**, not when the last one ends. Resolving at lift-off meant the brush reloaded with whatever colour was selected *then*, so choosing a new colour and painting again silently kept using the old one — caught by the reservoir-depletion test, which measured a stroke that laid down nothing because it was still holding the previous stroke's white.
- 40 Node checks on the colour model ([mixer.ts](app/lib/mixer.ts)); 16 in the browser. The browser test works on an opaque white ground with an indigo band and the foreground swapped to white, so the two behaviours separate cleanly: a **dry** brush carried the band's colour 0 px outward (reach 71 → 71, it was laying down its own white), a **wet, heavy-mix** brush dragged it to x=93, and smudge still reached x=142. A dry stroke's trail measured 67.5 → 17.6 → 0.1 → 0 as the paint ran out.
- **Not yet**: the **Tip shape** options (texture, dual tip, roundness/angle, scatter). They all live on the baked-tip path, which the mixer does not use — it drags a live pixel buffer rather than stamping a pre-rendered dab — so each would need a second implementation here rather than simply being switched on. Texture additionally wants the pattern-asset picker that fill layers and pattern text fills defer to.

### Merge visible & Stamp visible

- **Merge visible** (Layer menu) collapses everything currently on screen into one layer; **Stamp visible** (**Ctrl+Alt+Shift+E**) builds the same flat composite as a *new* layer and leaves every original alone. Both composite through the engine's existing `rasterize`, which already honours visibility — the only difference between them is whether the source leaves are freed.
- **Nothing hidden is ever destroyed, and this is where it diverges from Photoshop.** Photoshop's Merge Visible will consume a hidden layer that happens to sit inside a visible group. Here a visible group containing hidden children survives as a group holding exactly those children, with only its visible content merged out. Losing work you had merely switched off — and could not watch disappear — is not a trade worth making for a tidier tree. Verified in the browser by switching the layer back on afterwards and confirming its artwork is byte-identical.
- The merged layer takes the position **and the name** of the bottom-most node that had visible content, matching Merge Down and Photoshop. Everything left in the tree is hidden by definition, so that placement is invisible today; it decides what sits above what when someone switches a hidden layer back on.
- Stamp inserts **directly above the active layer** when that layer is top-level, and at the very top otherwise. The fallback is deliberate: a flattened copy of the whole document dropped inside a group would be clipped by that group's mask and blend, so it would not look like the thing it is a copy of.
- Merge refuses when it would do nothing — when the visible document is already a single plain top-level layer. A lone layer that carries a mask, effects, filters, a non-Normal blend or opacity below 100 is *not* a no-op, because merging bakes those; the check tests for exactly that rather than counting layers.
- Both read `active.layers`, never the isolate-derived view, so [isolate mode](#isolate-mode) cannot leak into a document operation.
- **The invariant worth testing is that the picture does not change** — a merge that alters the composite has lost or reordered something, which a layer-count check sails straight past. Measured: 3 layers → 1 with a byte-identical composite; a stamp whose layer alone reproduces the original composite exactly with every original hidden. (Note the composite is *not* identical while the originals still show underneath a stamp — an opaque copy over anti-aliased edges raises their alpha. That is correct, and is why it is measured with the originals switched off.)
- 55 Node checks on the tree logic ([merge-visible.ts](app/lib/merge-visible.ts)), 18 in the browser across four fresh-document scenarios.

### Isolate mode

- **Ctrl+Alt+L**, Layer ▸ Isolate layers, or the button in the Layers panel footer: solo the selected layers on the canvas. A persistent **Isolated** chip in the status bar is the way out, and the layers being hidden are *dimmed* in the panel rather than removed from it — they are still in the document, and filtering them away would make a viewing aid feel like a destructive one.
- **It is a view state, and the implementation is what makes that true rather than a promise.** Isolation is applied by deriving a tree for the canvas — `applyIsolation(active.layers, …)` feeds `CanvasArea` while every other consumer keeps reading `active.layers`. Nothing writes a `visible` flag, nothing pushes history, nothing is saved in the `.gproj`. Verified by flattening the image *while isolated*: the flatten produced a composite byte-identical to the all-layers one, which it could not have done if isolate worked by setting visibility. Also checked: the panel's eye states are unchanged and the History panel gained no step (7 → 7).
- **The rule, in full**: anything outside the isolation is hidden; the isolated nodes and their descendants are left exactly as they are, so an isolated layer's own eye still means what it always meant (isolating a *hidden* layer correctly shows nothing); and their **ancestor groups are forced visible**, because a group is a container rather than content — isolating a layer inside a hidden group and getting a blank canvas would just look broken.
- `applyIsolation` returns the **same array** when nothing changes, and rebuilds only the branches that do. The render graph keys off node identity, so a fresh tree every frame would throw away every cached layer for nothing.
- Held with the document id, so switching tabs cannot leave you looking at another document's isolation, and normalized against the tree each render — if the layers you soloed are deleted the isolation ends rather than sitting there hiding everything with nothing to show. Undo brings the ids back and therefore the isolation too, which is coherent (undo restored the state you were in) and never silent: the chip reappears with it.
- 36 Node checks on the pure rule ([isolate.ts](app/lib/isolate.ts)), 22 in the browser.

### Layer comps

- A **Layer Comps** panel (Window ▸ Layer Comps): named snapshots of layer **visibility**, **position** and **appearance**, with per-comp V / P / A toggles on the row so which attributes a comp records is visible and changeable without a dialog. Applying one is a single history step; a dot marks whichever comp the document currently matches (`compIsCurrent`, compared only over the attributes that comp actually captured — a visibility-only comp stays "current" whatever the opacities are).
- **Position is the interesting one, because this engine has no layer offset.** A layer here IS a full-canvas raster and moving it rewrites pixels, so there is no coordinate to store. A comp records the layer's **content bounding box** instead, and applying it translates the pixels by the difference between the recorded origin and the current one — reusing the same `layerContentBounds` + `offsetLayerPixels` pair that Align & Distribute already runs on.
- That choice comes with an exact guard, which is the point rather than a caveat: a translation moves a bounding box without reshaping it, so if the current box is a different **size** the content changed since capture (painted on, filtered, or dragged partly off-canvas and clipped) and the recorded origin no longer describes it. The comp then refuses to move that layer and says so in a toast. A silently wrong position is worse than an honest "this one moved on" — verified in the browser by painting on a layer and confirming it stays put while the toast names the reason.
- Applying **replaces rather than merges** the appearance fields: effects, fill opacity, knockout and Blend If are written even when the comp holds `undefined`, so a comp taken before a drop shadow existed can take the shadow back off. Layers created after capture are left alone (and counted), layers that have since been deleted are counted as missing; both are reported rather than silently absorbed.
- **The pixel moves and the tree change are one undo step.** The engine's `captureLeaves`/`restoreLeaves` snapshots ride in the same structural entry as the layer tree, so a comp cannot be half-undone into a state that never existed.
- Saved in `.gproj` (**format v21**). Comps are keyed by layer id and the loader **mints fresh layer ids** so an opened project cannot collide with open documents — so they are re-keyed through the same map on load, and keys with no mapping are dropped rather than kept as dead ids. Caught by reading the loader, then verified end to end: save a comp, reopen the file, move the artwork, apply — the layer returns to the recorded place.
- 70 Node checks on the pure model ([comps.ts](app/lib/comps.ts)); 31 in the browser across two drivers (apply, the position guard, single-step undo, the attribute toggles, duplicate/delete, and a full save → open round trip through the no-File-System-Access fallback paths).

### Layer style presets

- A **Styles** pane at the top of the Layer Style dialog's rail: a grid of click-to-apply looks, with **save** (capture what this layer is wearing), **import** and **export** (`.gstyle` files, `.astyle` accepted). Seven ship built in — Soft Shadow, Emboss, Ink Stamp, Neon, Gold Foil, Outline, Glass — chosen so that between them they use **every one of the eight effects**, which a unit test enforces so the set cannot quietly lose coverage as it is edited.
- Deliberately the same system as gradient presets ([styleio.ts](app/lib/styleio.ts) mirrors [gradientio.ts](app/lib/gradientio.ts)): same localStorage shape, same versioned JSON envelope, same `showSaveFilePicker`-with-download-fallback, same import rule — imported styles are **added** and colliding names are suffixed rather than overwritten, so a file can never destroy a library.
- A style carries the eight effects **plus** fill opacity, knockout and Blend If. It deliberately does **not** carry the layer's opacity or blend mode: Photoshop's styles do, but those two read as composition rather than decoration, and having "apply a style" quietly set a layer to Multiply at 60% is the kind of surprise that stops people using presets. Everything a style does change is visible in the dialog it was saved from.
- Applying is a **replace, not a merge** — a preset that carries no knockout writes knockout back to *None*, or a plain style dropped on a knocked-out layer would keep the hole and not look like the tile that was clicked. That is also why it goes through a dedicated single-step history op: the fill-opacity and Blend-If handlers are *live* doc patches (they fire per pointermove and would otherwise bury the undo stack), so routing a preset through them would let one undo take back the effects and leave the blending behind.
- **Thumbnails are rendered by the real effects pipeline**, not drawn as little pictures — each tile hands `renderStyled` a rounded slab and shows the result, on a fixed neutral ground rather than a theme colour so a style looks the same in the picker as it will on the canvas. They resolve the document's global light too, so a tile shows the angle the layer will actually get.
- 58 Node checks on the pure IO (capture, replace-semantics, sanitising, file round trip through the real serializer, merge, storage). In the browser, 19: applying Soft Shadow spread ink 1592 → 2954 px with the artwork byte-identical; Outline (fill opacity 0) took the layer's own pixels to alpha 0 while leaving 324 px of stroke; one undo restored the whole thing to the same composite hash; and saving a style, moving the layer to a different look, then re-applying reproduced the original composite **exactly**.

### Type effects from the Text tool

- An **FX popover** in the Text tool's options bar (beside Warp and Text fill) toggles and edits **drop shadow, outer glow, inner glow and stroke** without leaving the type context, plus three one-click presets — **Soft shadow, Neon glow, Outlined**.
- Nothing re-implements the shadow/glow maths. These are the same `LayerEffects` the Layer Style dialog edits and the engine already renders from a layer's alpha, so anything set from the Text tool is visible and editable in Layer Style, is non-destructive, and re-applies automatically whenever the type re-renders.
- What IS text-specific is the policy: seeds are **fractions of the font size** rather than the artwork defaults, because a 10 px shadow at 8 px distance is a fine drop shadow under a photo and a smear under 24 px type — a 24 px face seeds size 4 / distance 3, a 200 px face size 32. The seeded stroke sits **outside** so it cannot close up counters or thin the face, and its ink is chosen by luminance against the text colour so it is always visible. Presets **replace** the four type effects but preserve anything the popover does not surface (bevel, overlays), which can only have been set from the full dialog.
- A new text block has no layer yet, so the choice rides `TextSettings.fx` until commit — exactly as Warp and the gradient fill do. On re-edit it is seeded back **from the layer**, so the popover always shows what is actually applied. Same preview caveat as Warp: effects render on the committed raster, not on the live contentEditable overlay, so they appear once you finish editing.
- Measured in the browser, each in a fresh document: plain "EFFECTS" 2737 ink px, Outlined 3596, Neon glow 11218.

### Global light

- One lighting angle, held on the **document**, that effects opt into with a **Use global light** toggle. A drop shadow at 120°, an inner shadow at 30° and a bevel lit from 90° is the usual way a layer style stops looking like an object and starts looking like three unrelated decorations; global light is the fix, and new shadows and bevels follow it by default.
- Only three effects have a direction — **drop shadow, inner shadow, bevel** — so only those participate. Glows radiate and overlays are flat. The bevel also takes **altitude** from the light, for the same reason it takes the angle: a bevel lit from a different elevation contradicts the shadows just as visibly.
- Dragging the Angle slider on an effect that follows the light **steers the whole document**, rather than detaching that one effect — which is the point of having a shared light, and is why the toggle sits right beside the slider. Turn it off and that effect keeps its own angle, stored independently, so re-enabling restores what you set.
- Resolution happens at render time and never mutates the stored style, so an effect that opts out keeps its own value and a *disabled* follower keeps its stored angle rather than being quietly rewritten. The light is document state, so it is folded into the render key separately — the per-layer effects hash cannot see it change, and without that the cache would happily serve a stale shadow.
- Verified with two layers, each carrying a drop shadow: steering the angle from one layer's dialog moved **both** shadows by exactly the same delta (−14.7, −20.9 px). Saved in `.gproj` (**format v20**); older files fall back to the default 120°/30°, which is what every effect in them was authored against.

### Blending Options — fill opacity & knockout

- **Fill opacity** scales a layer's own PIXELS but leaves its effects at full strength — a layer at fill 0 with a drop shadow keeps the shadow and loses the artwork. That is the one thing separating it from plain opacity, and it is applied at exactly one point: the layer-fill draw inside the effects renderer.
- **Knockout** (None / Shallow / Deep) punches the layer's shape through what is beneath it, then paints the layer back over the hole. **Shallow** stops at the bottom of the containing group; **Deep** goes through the whole document. The punch uses the layer's OWN pixels, never its styled buffer — knocking out by a drop shadow would eat a soft halo out of the backdrop.
- The two ship together because knockout is invisible without fill opacity: at fill 100 the layer covers the hole it just made and nothing appears to happen. Verified exactly that way, without relying on colour: deep knockout at fill 100 leaves the composite untouched (alpha 255), at fill 0 the centre goes fully transparent (alpha 0), and switching knockout back off at fill 0 reveals the base layer intact.
- **Deep is done by propagation, not by a final root punch.** Unioning every deep shape and punching it out of the finished composite is the obvious implementation and it is wrong — by then the knockout layer has painted itself back over its own hole, so the final punch erases the layer too, and a hole appears even at fill 100 where there should be none. Instead each group render collects its descendants' deep shapes and the parent punches them just before drawing that group, so the shape escapes outward one level at a time. A top-level layer needs none of this: its inline punch already lands on the root accumulator.
- Both fields default to absent and are only written to `.gproj` when they differ from the default, so untouched layers gain nothing. **Blend-If** (this-layer / underlying, with Alt-drag split handles) was already present and unchanged; these complete that Blending Options group.

### Refine edge

- **Select ▸ Refine edge…** — **Smooth**, **Feather**, **Contrast** and **Shift edge**, previewed against **white, black or a rubylith overlay**, plus colour **decontamination**. The backdrops are not decoration: a soft edge is invisible against a background of its own colour, and fringe contamination only shows against a contrasting one — overlay tells you *where* the boundary is, white and black tell you what the fringe is *made of*.
- It extends the existing selection model rather than replacing it. Selections here are `Rect[]` geometry plus a softness applied when the mask is built, not a stored grayscale raster, so the whole refinement is a pipeline over the mask's alpha plane: a refined selection stays as cheap to store and as easy to transform as a plain one, and **every existing consumer of the mask picks it up for free**.
- **Order is load-bearing.** Smooth blurs then *re-thresholds* (that is what rounds off a staircase without softening it), so running it after Feather would throw the softness away; Contrast and Shift come last because both need a ramp to act on — against a hard binary mask, Shift can only move a boundary by whole pixels or not at all, so the pipeline injects a minimal ramp when Shift is used alone.
- **Contrast and Shift are one affine remap, not two independent knobs.** The gain has a floor derived from the shift (`gain ≥ 0.5 / min(t, 1−t)`); without it, moving the threshold on a unity-gain ramp translates the whole plane and the fully-unselected exterior comes back at 50% instead of staying at 0. The honest consequence, which Photoshop hides: a large Shift necessarily hardens the edge, because a ramp with pinned ends cannot move far without steepening.
- **Decontamination** inverts the mixture rather than desaturating the fringe. A soft-edge pixel *is* `C = a·F + (1−a)·B`, which is why an object lifted off a blue sky keeps a blue halo however good the mask is; given an estimate of B it inverts exactly as `F = (C − (1−a)·B) / a`. B is estimated only from pixels that are essentially **fully outside** — weighting every pixel by `1−a` instead lets the contaminated fringe vote for its own background and clears barely half the cast (measured: fringe blue 131 → 110 that way, 131 → **41** against a true foreground of 40). Below 15% alpha the inversion divides by almost nothing and amplifies noise, so it is left alone. Edge settings are non-destructive; decontamination edits pixels and is its own undo step.

## Performance & caching

- **Per-layer `pixelVersion`** (bumped at every committed pixel write — strokes, fills, gradients, shapes, paths, adjustments, text, load, duplicate, merge, undo/redo) + a document **`docEpoch`** (bumped on resize/crop/transform/colour-space) form the cache keys for effects/tone. Painting on one layer never invalidates another's styled cache.
- **Effects** composite as a single `drawImage` of the cached styled buffer when idle. **Tone** LUTs are built once per spec change and applied as one typed-array pass. **Clip groups** add one buffer + one composite pass per group (the `destination-in` clip is GPU, no per-pixel JS).
- Group and clip-group buffers are **fresh per composite** (nesting-safe) — consistent with the existing group compositing; pooled buffers are used only where re-entrancy can't occur.

## Persistence (`.gproj`, format v18)

- A self-describing JSON: doc name/size, foreground/background, active/selected layers, selection, and the layer tree. **Pixel layers** serialise as PNG data-URLs; **masks** (layer + filter) as grayscale PNG data-URLs + `{enabled, linked}`; **adjustment specs**, **layer effects**, **smart filters**, and **clipped** flags as plain JSON. Adjustment/effect/clip nodes carry **no raster** — they re-render from params on load. Later versions added metadata (v9), stored pen paths (v11), fill layers (v14), text warp (v15), gradient text fill (v16), ruler guides (v17) and **saved selections** (v18, names + grayscale rasters).
- **Backward-compatible:** older files (any earlier version, missing mask/effects/adjustment/clipped fields) open unchanged with those features simply absent.
- Tool options, colours, marquee shape/apex, view toggles, and theme persist separately in `localStorage`.
- **Units & resolution:** rulers and size readouts in **px / in / cm** (Preferences ▸ Units & rulers); documents carry a **resolution (ppi)** — defaulted from Preferences, set per document in New document, saved in `.gproj` — which drives physical-unit rulers, the status-bar size readout, the Metadata panel's physical size, and **true-size printing**.
- **Transparency grid** (Preferences ▸ Transparency): the checkerboard behind transparent canvas areas is configurable — square size (**None / Small 8 px / Medium 16 px / Large 24 px**; screen-space, so squares keep their size at every zoom) and colours (**theme-following greys** by default, the classic **Light/Medium/Dark** grey pairs, or a **custom two-colour pair** via colour wells) with a live preview in the dialog. "None" shows a flat backdrop instead of squares. The small UI-chrome checkers (colour-picker alpha strip, navigator, dialog thumbnails) deliberately stay theme-based.
- **Files tab (Preferences):** the file-handling settings in one place — the **autosave interval**, **export defaults** (the format Export As opens with, limited to formats the browser can really encode, plus a default quality), the **recent-files length** (4–20; the store trims as new entries are added), and the **shared-gradients library toggle**.
- **Settings reset / portability:** the Preferences footer has **Restore defaults…** (resets every setting — tool options, panel layout, theme/accent, colour management, all Preferences — while keeping saved gradients, swatches, presets, recents and autosave snapshots) plus **Export/Import settings** as a portable `graphiq-settings.json`; imports are validated against a strict key whitelist and apply via reload.
- **Autosave & crash recovery:** **all open documents** snapshot to IndexedDB on a Preferences interval (default every 2 min, only when something changed); a heartbeat flag detects unclean exits and offers **Restore / Discard** on the next start — restoring reopens every tab and re-activates the one that was in focus. The status bar shows the real save state ("Unsaved changes" / "Saved" / "Autosaved HH:MM") along with the true document colour space and a Photoshop-style flattened/all-layers size estimate.
- **Keyboard shortcuts — one registry, remappable:** every tool key and menu shortcut resolves through a single registry (`shortcuts.ts`, defaults derived from the tool/menu definitions), which drives the **actual key dispatch**, the labels in the menus and the `Ctrl+K` palette, and the **Keyboard Shortcuts window** — where any binding can be **remapped**: click the key chip, press the new keys (Backspace unbinds, Esc cancels); conflicts move the key from its current owner with a note, reserved bindings (paste's Ctrl+V) refuse, customized rows are marked with per-row restore and a "Reset all". Remaps persist locally and ride the settings export/import/reset. Fixed canvas gestures (wheel zoom/pan, marquee/lasso cycles, nudges) are listed for reference but not remappable.
- **Help & About:** a **Help window** (Help ▸ Getting started / Documentation) with a 7-step quick-start walkthrough and a **searchable reference** of ten topics — tools, selections, layers & masks, adjustments & colour, filters & effects, text & vector, open/save/export, colour management, view & workspace, storage & privacy — hand-curated in `app/lib/help.ts` (topic nav like Preferences; the search filters entries across every topic). **Help ▸ About** shows the app version (from `package.json`), the format matrix and the local-only privacy promise, and cross-links into the guide and the shortcuts window.
- **Storage panel ("scratch disks"):** Settings ▸ **Scratch disks / storage…** opens Preferences ▸ **Storage** — the honest browser equivalent of scratch-disk management: the origin's **storage estimate** (used vs available with a meter, via `navigator.storage.estimate()`), **persistent-storage** status with a request button (protects autosave/recents from browser eviction), and a per-store breakdown with confirm-guarded clear actions — the **autosave snapshot** (doc count, ~size, timestamp → Delete), the **recent-files list** (count → Clear), and **saved presets & swatches** (gradients, swatches, adjustment looks, export presets → Delete; settings themselves reset via the existing footer button). Settings ▸ **Performance…** deep-links Preferences ▸ Performance the same way (`initialTab`/`onTabChange` on the dialog — plain Preferences… reopens on the last-visited tab). All five former Settings/Help stubs now do something; every entry is reachable from the `Ctrl+K` command search.
- *Saved history is labels + index only* — the live undo stack (in-memory callbacks) is not replayable from a file.

## Tests

`npm test` (Vitest, config in `vitest.config.mts`) — **190 unit tests** over the DOM-free libs: `tone.ts`, `filters.ts`, `gradient.ts`, `render-graph.ts`, `layers.ts` tree ops and `view.ts`. `npm run test:watch` re-runs on save; `npm run check` is typecheck + tests. Whole run: ~0.3 s.

- **Plain Node, not jsdom.** The modules under test do arithmetic on numbers and trees; a browser environment would only add startup cost and *hide* an accidental DOM dependency instead of failing on it. The one thing Node lacks is `ImageData`, which `tests/setup.ts` supplies — deliberately faithful rather than convenient: it **wraps** the array it is given instead of copying (so "the filter returned a fresh buffer" is really being asserted) and validates lengths as the spec does. A lenient shim would let broken code pass here and fail in the browser.
- **Oracles over expectations, where one exists.** `invertRects` is checked by rasterizing input and output and demanding they be exact complements, across 200 seeded random rect soups — the awkward coincidences (shared edges, containment, zero spans) are exactly what breaks sweep algorithms, and random cases find them far better than hand-picked ones. Disjointness comes free from comparing summed rect area against the raster's pixel count. `tileRect` is checked the same way (summed tile area == document area proves no gaps *and* no overlaps), as is `rectsOverlap`.
- **Injected dependencies make "untestable" code testable.** `buildCanvasGradient` looks like it needs a browser, but the context is a parameter: a stub recording `addColorStop` turns the midpoint power curve, the reflected mirror and the angle-seam blend into ordinary arithmetic. The conic fallback is tested by omitting `createConicGradient` from the stub.
- **Invariants the codebase depends on, asserted directly.** `clipGroupsOf` is checked as a **partition** of its input — every node exactly once, as base or member — because a dropped node vanishes from the canvas and a duplicated one paints twice. The layer ops run over a **deep-frozen** tree, so an in-place mutation throws rather than silently rewriting history. `pruneLinks` is asserted to return the *same array* when nothing changes (a new one would invalidate every cached render for no reason).
- **The suite was itself tested.** 22 deliberate mutations of the six libs — LRU order reversed, `clampRect` rounding inward, `composeLUT` order swapped, the Fritsch–Carlson limiter disabled, mosaic averaging straight RGB, preview scaling applied to zoom/spin blurs — **22/22 caught**. The two that initially escaped were real gaps: the extremum-flattening branch needs a *non-monotone* curve to exercise it, and the mosaic transparency case needs transparent **white** (transparent black premultiplies to the same value either way, so it proved nothing).
- **It found a real bug on the first run.** `solveGrayPoint` returned the reciprocal of the gamma `levelsLUT` consumes, so the Levels grey-point eyedropper *amplified* a colour cast instead of removing it: sampling (200,150,100) gave (225,140,40) rather than that pixel's own grey, (159,159,159). The test that caught it does not compare gammas — it pushes the solved parameters through the real `levelsLUT` and asserts the result comes out neutral, which is the actual definition of the feature. Fixed and verified in the running app.

### Crash recovery (error boundary)

An error boundary wraps the editor (`ErrorBoundary.tsx`, mounted in `page.tsx`; the plumbing is `crash.ts`, 24 unit checks). A render crash raises a full-screen dialog offering **every open document** as a recovery copy, a **Copy report** for a bug, and a reload.

- **The registry is the design.** The collector that serializes the open documents lives at *module* scope and is registered by the editor, because React unmounts the editor before the boundary can respond — that closure is then the only thing left that can reach the user's unsaved work. It deliberately does **not** unregister on unmount either: effect cleanups run *before* `componentDidCatch`, so a tidy cleanup disarms recovery at precisely the moment it is needed. Both facts were measured, not reasoned — the first version reported "no recoverable work" while the pixels sat safely in the engine.
- **Layered.** Live documents first; if collecting them fails, the last IndexedDB autosave, with its age stated plainly ("from 4 minutes ago") so the user knows what they are getting.
- **Several documents leave as one zip.** Browsers throttle or silently block a page that fires downloads in a row — the same test run wrote five files once and two the next. Entry names are de-duplicated, since tabs can share a name and inside an archive a repeated name is one document overwriting another.
- **The report is safe to paste in public**: error, stack, component stack, version, browser, and the *shape* of the open documents (`Untitled-1 (12.4 KB)`) — never pixels, never file contents. The dialog says so.
- **Testing found four defects, three in code that pre-dated this work**: `throw undefined` produced a non-string message (`JSON.stringify(undefined)` is `undefined`), so the dialog would have shown nothing where the error goes; `..` survived the recovery-filename scrub; the snapshot collector skipped any tab whose JSON had never been cached, **losing three of five open documents** — which silently affected autosave too; and one-download-per-document hit browser throttling.
- **Known limit, stated in the code.** Boundaries only see errors thrown while *rendering*, and most of this app's work happens in pointer handlers, where a throw leaves the UI standing with one tool silently dead. Those are recorded (`noteRuntimeError`) as context for whatever crashes later rather than replacing a working editor with a crash screen — which would lose more work than it saved.
- Verified end to end: paint → crash → save → reload → open returns **byte-identical pixels**, and the smoke test carries a permanent crash leg covering the dialog, the zip, extraction of every entry, and the reopen.

### End-to-end smoke

`npm run smoke` (`tools/smoke.js`; `--keep` retains the artifacts) — 20 checks over the one journey that has to work or nothing else matters: boot, new document, paint, undo, redo, save, reopen, export. Every other tool checks one subsystem in depth; this one checks they are still joined together.

- **It asserts outcomes, not steps.** "Clicked Save and nothing threw" is worth nothing — the interesting failures are a project that saves but restores a blank canvas, or an export that writes a valid PNG of the wrong thing. So the composite is hashed before saving and again after reopening, redo is compared against the pre-undo hash rather than merely "ink is back", and the exported PNG is checked for its magic bytes, its IHDR dimensions, *and* decoded and compared with the canvas it came from.
- **The reopen goes into a different document first** (a 120×90 decoy), so a pass cannot come from the file never having been read.
- **The file pickers are deleted before boot.** With the File System Access API present the app opens a native dialog no automation can reach; removing it sends the app down its download and `<input type=file>` fallback — not a workaround but the path every browser without that API actually uses.
- **Proven to fail, in the right place.** Export at half scale trips the size and picture checks; a save that drops layer pixels trips the payload, round-trip and export checks; removing the undo action trips the undo check. A control rewrite trips nothing. The undo mutant was applied to the *menu* action while the test presses Ctrl+Z and still failed — both routes go through the one shortcut registry.

### Tracked benchmarks

`npm run bench` (`tools/bench-track.js`; `--filters-only` needs no browser, `--no-record` writes nothing) appends a record to `tools/perf-history.json` and compares it with the last one. It measures **filter throughput** (MP/s for all 19, in plain Node) and **composite time vs layer count** (1→32 layers in the real app, timed by the engine's own composite clock rather than by wrapping an export, whose PNG encode would dwarf it). It complements `npm run perf`, which gates *interaction blocking* against fixed budgets; this one has no budgets and never fails a build, because a benchmark that fails CI on a noisy machine gets muted within a week.

- **Every record carries its own calibration** — reference primitives measured in the same process, at the same moment — and comparisons are scaled by the ratio between two runs'. Absolute wall-clock cannot separate "the code got slower" from "this computer got slower", which is the lesson `tools/perf-suite.js` paid for with a bisect. The scaling is an estimate, not a fact, so differences are "flagged", never "regressed".
- **The runtime turned out to matter more than the code.** Under `tsx` the same benchmark file reported Add Noise at 128.7 ms; under plain `node`, 17.0 ms — a 7.5× gap from the transpiler alone, enough to misrank the filters entirely. It now bundles the module with esbuild and measures in plain node.
- **JIT tiering had to be warmed out.** With a single warm-up, run-to-run spread on *identical* code reached 67% (Add Noise), 51% (Dehaze) and 23% (Stylize) — and was bimodal rather than scattered, the signature of V8 tiering up part-way through a run. Four warm-ups bring most filters inside 5%.
- **The flag threshold is derived, not chosen.** Four runs over unchanged code put the worst spread at 20.6%, so it sits at 35%; at the 25% first tried, a clean re-run flagged Dehaze as a 27% "regression". The regressions this codebase has actually had were 1.4 s and up — multiples, not percentages.
- **It found a real bug on its first run.** Add Noise — a hash and three adds — ranked slowest of all nineteen filters, below Oil Paint and Median, because `rnd` was declared *inside* the pixel loop: ~400 000 closure allocations per pass. Hoisting it is **2.5× faster and byte-identical**, which the golden images proved by not moving.
- **What the composite series says.** With caches intact, composite time is 0.1–0.3 ms from 1 to 32 layers — at the browser clock's 0.1 ms resolution, i.e. plain compositing is a blit and effectively free. Cold, with every styled product recomputed, it is dead linear at **~90 ms per drop-shadowed layer** at 1920×1080. That corroborates the §8 measurement that the cost is all `renderStyled`, not compositing.

### Golden images

Property tests catch a pass that is *wrong*. They do not catch one that is merely *different* — a refactor that shifts every pixel two levels, a changed rounding rule, a kernel that quietly stopped premultiplying somewhere no property looks. So each pass is run over fixed fixtures and its output hashed, with the hashes checked in: a change to the numbers has to be looked at and accepted rather than arriving unnoticed.

- **Split by what each pass needs.** The pure ImageData passes — every filter, adjustment, extra adjustment and tone map — are golden-tested **in Node** (`tests/golden.test.ts`, 169 entries in `tests/golden/baseline.json`, inside `npm test`, ~0.4 s; re-record with `UPDATE_GOLDENS=1`). Layer effects cannot be: `renderStyled` composites through canvas shadows, blend modes and gradients, so the browser *is* the implementation — hence `npm run test:fx` (`tools/golden-effects.js`, baseline in `tools/golden/effects.json`, `--update` to re-record), which records each of the eight effects alone and then all eight together. Alone localizes a regression to one renderer; together catches the stacking order.
- **Both bit depths.** `applyAdjustments16` and the 65k-entry tone tables are second implementations of the same maths, not wrappers around the 8-bit ones. Nothing covered them until a mutation to the exposure formula changed no golden at all.
- **Fractional parameters, because every default is a whole number.** The half-resolution preview runs the stack through `scaleFilterParams`, and that path was unrecorded: changing mosaic's cell rounding from `round` to `ceil` moved nothing, since a cell size of 8 rounds the same either way. A preview-scaled family at 0.55 — deliberately not the literal 0.5, which leaves the params integral — closed it.
- **Fixture determinism is the real work.** The Node fixtures are built from integer arithmetic only: `sin`/`pow`/`sqrt` are not required to be correctly rounded, and there is no reason to take that risk on the *input* as well as the code under test. The effects fixture avoids a brush entirely — size, hardness, opacity and colour all persist in `localStorage`, so a painted silhouette would depend on the last session — and is instead a solid fill layer, its colour set through the scripting hook, flattened and masked to two rectangles from a numeric selection.
- **A guard that earned itself immediately.** The effects fixture originally *masked* the fill layer rather than applying the mask, and six of the eight effects recorded as no-ops: effects render from a layer's own alpha and the mask is applied to the **result**, so a full-canvas layer cast its shadow off the edge of the canvas and then had it masked away. The runner's "identical to the bare layer" check caught it; without it, six goldens would have been checked in as working and matched for ever.
- **Proven to fail.** 5/5 filter and adjustment mutants caught — mosaic cell rounding, noise amplitude, unsharp radius, and exposure and contrast scaling across both bit depths — with two *provably equivalent* mutations (posterize `/255` vs `/256`, which agree at every level count; a 2% radius change that lands on the same box-blur width) correctly staying silent. On the effects side, 4/4: a one-pixel drop-shadow offset, a 40% outer-glow blur, a 40% inner-shadow blur and a half-percent gradient-overlay angle each moved **exactly** their own golden plus `all-eight`, and nothing else.
- Baselines store per-channel means and ink alongside the hash, so a failure report says which way the pixels moved rather than only that they did.

### Pixel identity (the Spec 06 oracle)

`npm run test:pixel` (`tools/pixel-identity.js`; `--big` adds the tiled path, `--url` targets another port). Anything the compositor caches must be *provably* invisible: **a document composited with warm caches has to be byte-identical to the same document composited from scratch.** That one invariant covers the whole of Spec 06 — the dependency hashing in `nodeKey`, the intrinsic/extrinsic split in `effectiveKey`, clip-group and group buffers, tiled adjustment products, and eviction. It runs in a real browser, because the compositor's correctness depends on Chrome's canvas semantics; a headless canvas would be a different oracle.

- **15 stages, one document.** It is built up through the same paths the UI uses (`window.graphiq` command dispatch plus real brush strokes): mask, layer effects, non-Normal blend at partial opacity, adjustment layer, clipping mask, group, smart filter, mask-from-selection, parametric fill, a second adjustment, a repaint, an undo, a second filter, a mask repaint — plus a 4096² document for tiled products. After each stage the document is exported twice, once with the caches as the interaction left them and once with `__gqRenderCache.disable()`, and the two PNGs are compared byte for byte. Both go through `exportComposite`, so the cache is the only variable.
- **No product surface was added.** The debug toggle already existed (`setRenderCacheEnabled`, exposed dev-only as `window.__gqRenderCache`) — the TODO's `disableRenderCache` was a misremembered name.
- **The hard part is non-vacuity, not the comparison.** Byte-identity holds just as well when the cache was empty, when both runs bypassed it (a node under live edit bypasses by design), or when a stage's setup silently failed — and early drafts hit all three; positional layer targeting kept selecting the enclosing group or the un-paintable fill layer, leaving three stages comparing a document they had never changed. Each stage now proves, from the engine's own counters, that the cache had entries, that the first export reused them (a counted hit — or resident **tiles** on a big document, whose products are reused off the counted branch), that the second had none, and that the composite is both non-blank and *different from the previous stage*. Short of that it prints INCONCLUSIVE or NOT BUILT, never PASS.
- **Proven to fail.** Five dependencies were stripped from the cache key one at a time; **5/5 caught** — `pixelVersion` (stage 11, 9,082 px differ), the effects hash (stage 2, 1,429 px), the filter-stack hash (stages 13–14, 7,195/7,548 px), the mask version (stage 14, 802 px), and opacity+blend in `effectiveKey` (stage 9, 235,833 px).
- **Adding a dependency and changing one are different tests.** The last three of those only fell to the stages that change a dependency *already present*. Stages that merely give a layer its first filter or first mask miss them entirely, because adding one flips `hasEnabledFilters` / `mask.enabled` — so the key changes regardless of what it hashes those to.

# Part 3 — Known limitations / not yet implemented

Honest list of what is **partial, deferred, or absent**:

**Non-destructive stack gaps**
- **Filter-mask move:** the smart-filter mask always tracks its layer through canvas transforms; there is no unlinked per-mask move (the layer mask has one via the link toggle).
- **Curves targeted adjustment** (the optional spec item) is now implemented: the Curves dialog's **Target** toggle lets you click-drag on the image to shape the active channel's curve at the sampled tone — the dialog docks aside, the sampled value is **inverted through the current LUTs** so the point lands at the pre-curve tone, and dragging up/down moves its output. Honest limit: the sample reads the flattened view, so layers/effects *above* a curves adjustment node can skew the recovered tone.
- **Gradient stroke effect** shipped 2026-07: the Stroke effect's Fill switches between **Colour** and **Gradient** — the full multi-stop gradient editor (same preset library as the Gradient tool), with Reverse and an Angle control (overlay-consistent centred geometry; documents saved before the angle existed keep their original diagonal).
- **Clip edge case:** a clipped layer sitting directly above a **non-clipped adjustment layer** is treated as **inert** rather than clipping to the pixel base *below* the adjustment (a rare configuration; the spec permitted "inert" as a fallback).
- The **options-bar mask pill** shipped 2026-07: an accent-bordered "Editing mask" / "Editing filter mask" chip in the options bar, click to drop back to the layer's pixels; Quick Mask shows its own rubylith chip in the same slot. The Layers-panel active-surface ring remains alongside it, and the Channels-panel mask channel + Alt-click mask view shipped 2026-07.

**Performance (render graph — Spec 06 built)**
- The compositor now runs through a **key-validated per-node render cache**: unchanged subtrees are never recomputed (a cached group/effect/adjustment product is one `drawImage`), opacity/blend/visibility changes reuse the layer's intrinsic render, and adjustment layers only re-run their read-back when something *below* them actually changed. A byte-budgeted LRU bounds memory, live brush strokes bypass the cache, and a dev toggle (`__gqRenderCache.disable()`) A/B-verifies pixel identity against the uncached path.
- The LRU byte budget is configurable in **Preferences ▸ Performance** (64–1024 MB slider) with live statistics — memory used vs budget, cached-product count, and the session hit rate. The same tab caps undo by **both** a step count (10–200) and a **memory budget in megabytes**, whichever is reached first, with a live meter showing what the stack currently holds; trimming drops abandoned undo-tree branches before anything still reachable. It also offers a **background-workers toggle** (off = every heavy path runs its synchronous fallback, a debugging aid).
- **Web Worker offload** covers the three heaviest compute paths: the Blur Gallery (session originals cached in a worker, per-tick param messages, stale replies dropped), the heal brush / content-aware fill (the membrane solve runs off-thread; replies are validated against the document state captured when the job was posted, with a synchronous fallback), and **smart-filter recomputes** (the whole stack renders in a worker with a stale-while-refresh product cache — while a recompute is in flight the compositor draws the previous product, so filter-param drags stay fluid; live painting on a filtered layer and the destructive "Apply (bake)" stay synchronous for exactness).
- **Progressive preview**: on documents over ~2 MP, filter-param drags compute at **half resolution** (spatial params scaled to match, result upscaled) so the preview tracks the slider closely; the moment the params settle, a full-resolution pass refines it in the background. Exports never contain preview-quality pixels — anything but an exact full-quality cache hit re-renders synchronously at full resolution.
- **GPU tone stage (WebGL2)**: Curves/Levels adjustment layers render through a shader LUT pass when available — the accumulator uploads straight to a texture (no `getImageData`), a 256×1 LUT texture maps each channel to its exact 8-bit bucket, and the result comes back by GPU→GPU `drawImage`. Falls back to the always-correct Canvas2D path on missing WebGL2, unsupported wide-gamut plumbing, or context loss; byte-certain exports always use the CPU path; A/B via `__gqGPU` in dev.
- **Region-scoped adjustment recompute**: when only a rect-bounded change happens beneath an adjustment layer (a brush commit, a heal, an undo patch), the adjustment re-reads and re-processes just that rect and reuses the rest of its cached product — adjustments are strictly per-pixel, so the result is byte-identical. Changes with pixel *reach* (layers carrying effects or smart filters, or inside styled groups) automatically fall back to the safe full-document path.
- **Tiled adjustment products (very large documents)**: once a document is big enough that one full-size cached product rivals the whole cache budget (≥ 64 MB — ~4k×4k, so every 8k+ document), adjustment products are cached as a grid of **1024-px tiles** instead of one giant canvas. Eviction frees individual tiles (exactly the overage, LRU-first) instead of dropping a ~268 MB product wholesale; an evicted or dirty tile is recomputed **alone** from the below-accumulator (the math is strictly per-pixel, so a lone tile is byte-identical to the full pass); and rect-bounded commits — brush strokes, heals, undo patches, and **mask paints on the adjustment itself** — re-render only the touched tiles, with none of the old per-commit full-canvas copy + allocation. GPU tone products are never patched with CPU tiles (sub-LSB seams): any staleness there takes the cheap readback-free full GPU pass and re-slices every tile from that single source. The Preferences ▸ Performance stats show resident tiles.
- **Draft-resolution filters AND layer effects during a live gesture**: while you are painting, dragging or transforming a layer that carries smart filters **or layer effects** (shadows, glows, bevels, strokes), they run at a reduced working size (scaled so one frame stays near a ~0.5 MP budget, never below quarter scale) with its spatial params scaled to match, then upscales — a real filter pass over fewer pixels rather than a frozen or missing preview. The moment the gesture ends the normal path recomputes at full resolution, so what you commit is never the draft. This is the difference between a filtered layer being usable and not: a selection drag with one blur went from **4684 ms of main-thread blocking to 69 ms** (26 long tasks to 1), a brush stroke on a filtered layer from **3865 ms to 128 ms**, and a stroke on a layer with a drop shadow from **1390 ms to 64 ms**. For effects the cost was never the blur kernel — the same shadow at maximum size measured 1450 ms against 1390 at the default, because the per-call full-canvas setup dominates — so shrinking the surface was the fix rather than a faster kernel. Exports are explicitly excluded (a live session cannot leak draft pixels into a saved file), and the frame that settles a gesture repaints the whole view so no draft pixel can linger outside the last dirty rect.
- **Region-scoped changes through styled layers**: a pixel change under a node that spreads pixels no longer forces a full-document repaint. `reach.ts` computes how far each effect and filter spreads (a blur by its radius, a shadow by distance + blur, find-edges by 1, posterize by 0) and the change rect is grown by that much instead of discarded — a brush stroke on a layer with a drop shadow blits ~2% of the canvas rather than all of it, byte-identical to the full pass. Filters whose output depends on a pixel's ABSOLUTE position — twirl/pinch/wave, mosaic (origin-anchored cells), noise (per-index seed), zoom/spin blur (anchor-relative), tilt-shift (absolute band) — cannot be region-scoped at any padding and correctly fall back to the full pass.
- **Cache-blocked blur** — the separable box blur behind every shadow, glow and blur filter did its vertical pass one column at a time, striding through memory by the image width, so each 64-byte cache line fetched yielded a single useful float. It now blurs **16 columns at once**, and because every column keeps its own running sum in the original order, the arithmetic is unchanged and the output is **bit-identical**, not merely close. The vertical pass alone dropped from 3.4× the cost of the horizontal pass to roughly parity; end to end the blur is **1.30× faster at 1920×1080 and 1.67× at 4000×3000**, which took a stroke-plus-settled-full-resolution-pass on a 12 MP document with a drop shadow from **419 ms of blocking to 323 ms**. Bit-identity is not a nicety here — blur output feeds what you see *and* what you export, so the two must agree; [tools/verify-blur-identity.ts](tools/verify-blur-identity.ts) pins the shipped code to the original implementation byte-for-byte across 35 shapes, and caught a real defect during development (accumulating the running sums in a 32-bit array rounds at every step, where the original accumulates in a double and rounds only on store — the output looked right and was wrong in the low bits).
- **No redundant silhouette mask in layer effects** — rendering a layer's effects built a full-canvas alpha mask of the layer, on *every* call, whether or not any enabled effect needed one (~31 ms at 4000×3000). Every use of it is a `destination-in`/`destination-out`, which reads the source's alpha channel and nothing else — and the layer's own canvas already carries exactly that alpha, so the mask was pure overhead. Together with the cache-blocked blur, a brush stroke plus its settled full-resolution pass on a 12 MP document with a drop shadow went from **419 ms of blocking to 282 ms**. Verified unchanged by an A/B hash over a five-effect composite ([tools/ab-effects.js](tools/ab-effects.js)) — which also *rejected* two changes that looked equally safe: dropping the `willReadFrequently` hint on the mask canvas was 10 ms faster but silently dropped 445 of 21,788 non-empty pixels, and writing whole pixels through a 32-bit view was 25% faster but truncates where the byte store rounds half-to-even, disagreeing on roughly half of all fractional samples. Reasoning had called all three safe; only the measurement separated them.
- **Interaction performance regression suite** (`npm run perf`, [tools/perf-suite.js](tools/perf-suite.js)): seven scripted gestures — a plain stroke, a stroke on a blur smart filter, a selection move over a filtered layer, a stroke on a drop shadow, a stroke on a per-pixel stylize filter, ten magic-wand add-clicks, and a 30-step Apex sweep — each measured by `PerformanceObserver('longtask')` (main-thread blocking, the thing that feels stuck) against a per-scenario budget, exiting non-zero on a regression. Frame intervals are deliberately *not* asserted: headless Chrome runs rAF unthrottled, so a "4 ms median frame" would be an artefact of the harness. Two properties make the numbers trustworthy. **Scenarios are isolated** — each builds its own layer and deletes it again, because sharing one document made the per-pixel case read 151 ms that was entirely the blurred and shadowed layers left below it from earlier scenarios; a layer-count invariant between scenarios fails the run if a teardown ever stops working. And the **invariant is itself tested**: `GQ_PERF_SELFTEST=1` disables teardown on purpose and the run must fail, so the guard is never silently dead. Budgets sit ~4–6× over the measured figure, which passes ordinary noise while catching the regressions that actually happened here — every one of them 1.4 s and up. The run also **calibrates the machine first**, on a bare canvas before the app loads, because absolute wall-clock budgets cannot by themselves tell "the code got slower" from "this machine got slower" — and the second does happen: the same commit scored 7/7 and then 2/7 hours later, with an app-independent benchmark showing the machine itself had become 2× slower. When calibration is off baseline the suite says so, twice, rather than letting a red run be misread as a code regression.
- **Restoration & detail filters** (smart-filter types, so they stay re-editable): **High Pass** keeps detail finer than its radius and flattens the rest to mid-grey — blend it Overlay/Soft Light above the layer for frequency-separation sharpening. **Median** replaces each pixel with its neighbourhood median, which kills speckle while keeping edges straighter than a blur does. **Dust & Scratches** is the same median applied *only* where a pixel disagrees with it by more than a threshold, so defects go and the rest of the picture is left alone (at threshold 0 it is exactly a Median — an invariant checked both in isolation and end-to-end through the UI). **Reduce Noise** is the denoise-tuned sibling of the Surface blur: rather than bilaterally averaging RGB together, it splits the image into luma and chroma, runs the edge-aware average on luma only, and blurs the two chroma planes outright — because sensor colour speckle is coarser and more objectionable than luma grain, and edges live in luma. The median uses a sliding 256-bin histogram with an incrementally tracked median (Huang) rather than sorting each window, which is what makes a radius of 16 practical at all; it is verified against a naive per-window sort, exhaustively, across seven image shapes and a varying-alpha case. All four declare a finite pixel *reach*, so unlike Twirl or Mosaic they can be region-scoped, and all four scale their radius for the half-resolution preview so the preview shows the filter you will get. Costs at 1920×1080, full resolution, in the worker: High Pass 140 ms, Reduce Noise ~390 ms, Median 459 ms at radius 2 rising to 2.0 s at the maximum radius of 16.
- **Lens Corrections** (smart-filter type): geometric distortion (barrel/pincushion), lateral chromatic aberration (separate red/cyan and blue/yellow sliders) and vignette (darken *or* lighten, with a midpoint controlling how far out the falloff starts) — in **one resampling pass**. Distortion and chromatic aberration are both radial remaps, so shipping them as two stackable filters would resample the image twice and visibly soften it; here each output pixel resolves its source position once, and the fringe correction is simply a per-channel tweak to that same radial scale, which is what lateral CA physically is. Sampling is bilinear on premultiplied channels — CA shifts are sub-pixel by nature, so nearest-neighbour would quantise away the very thing being corrected — and each channel is unpremultiplied against the alpha sampled at *its own* position, since using green’s alpha for all three would tint the fringe being removed. The radial model normalises so the image CORNER is 1.0, which makes every parameter resolution-independent: the half-resolution preview shows the same correction (verified — a 61 px and a 121 px render agree at the same relative position), and there is nothing for the preview scaler to scale. When distortion and both fringe sliders are 0 the resample is skipped entirely and only the vignette runs, which is the common case and takes it from 198 ms to **44 ms** at 1920×1080 (all three corrections together: 187 ms). Being centred on the image, it is position-dependent and correctly declines region-scoping, exactly like Twirl and Pinch.
- **Photographic filters** (smart-filter types). **Dehaze** uses the dark-channel prior: haze is additive veiling light, so in a hazy patch no colour channel is ever really dark, while almost every haze-free outdoor patch has some channel near zero somewhere — that gap estimates the veil, which is then inverted out. Two deliberate departures from the paper: atmospheric light is averaged over the brighter half of the haziest 0.1% of pixels rather than taken from the single brightest pixel (one blown highlight would otherwise set it, and averaging *all* candidates under-estimates it — measured as a 26% contrast overshoot past the haze-free reference, cut to 14% by the fix), and the transmission map is refined with a blur rather than a guided filter, which is edge-unaware so very strong settings can halo along a hard skyline. **Clarity & Texture** is local contrast at two scales — broad shaping and fine detail — but differs from stacking Sharpen twice in two ways that matter: it works on luma and rescales RGB by the ratio, so contrast does not drag saturation with it, and Clarity is midtone-weighted (falling to zero at pure black and white), which is what stops it carving halos into skies. **Grain** is film grain rather than per-pixel speckle: noise is generated on a coarse lattice and interpolated up so it forms clumps of a chosen **size**, a second much coarser field modulates its amplitude so strength varies across the frame (**roughness**), and it is weighted to the midtones because film shows little grain in deep shadow or blown highlight — skipping that is what makes synthetic grain look pasted on. Cost at 1920×1080: Dehaze 215 ms, Clarity & Texture 99 ms, Grain 80 ms. Clarity declares a finite reach and can be region-scoped; Dehaze cannot, for a reason unrelated to kernels — its atmospheric light is a statistic over the whole image, so a region would recover different colours — and Grain cannot because its lattice is anchored to the image origin.
- **Stylistic filters** (smart-filter types). **Oil Paint** gives each pixel the average colour of whichever intensity bucket dominates its neighbourhood — taking the modal bucket rather than the mean is what produces flat strokes with hard boundaries instead of a blur; it reuses Median’s sliding-window trick (a column out, a column in) so it costs O(r) per pixel, which is what makes a 16 px brush usable at all. **Halftone** is a real printing screen rather than a texture overlay: each pixel finds its cell in a *rotated* lattice, reads the source at that cell’s centre, and becomes a dot whose AREA tracks the value — hence radius ∝ √value. Colour mode screens cyan, magenta and yellow 30° apart, which is not decoration: screens at similar angles beat against each other into moiré. **Crystallize** is a Voronoi mosaic — one jittered site per grid cell, each cell flooded with its own average colour; jittering is what separates it from the square Pixelate grid, and searching only the 3×3 neighbouring cells is exact because a jittered site can never beat one from further away. **Glitch** tears whole bands rather than individual rows (per-row noise reads as static, not as a broken signal), separates the channels after displacement so the fringe rides along with the tear, and darkens alternate rows for scanlines. **Drop Shadow (baked)** exists for the one case Layer Style ▸ Drop Shadow cannot serve — a shadow that later filters in the stack can see, because it is part of the pixels by then. For everything else the layer effect is better: live, re-editable, and free to spill outside the layer, whereas this one is clipped at the layer bounds since filters never enlarge a layer. Cost at 1920×1080: Glitch 25 ms, baked shadow 74 ms, Crystallize 93 ms, Oil Paint 199 ms (457 ms at the maximum brush), Halftone 318 ms. Oil Paint and the baked shadow declare a finite reach and can be region-scoped; Halftone, Crystallize and Glitch all snap to something anchored to the image origin (a rotated screen, jittered cells, band index from the top) and correctly decline.
- **Live filter previews in the picker**: every row of the Smart Filters "Add" list shows a thumbnail of **your own layer** run through that filter, so choosing one is a matter of looking rather than guessing from a name. The previews deliberately use each filter’s default params **unscaled**, which is the opposite of what `scaleFilterParams` does for the document preview — and the opposite is right here: scaled proportionately, a 12 px crystallize cell on a 56 px thumbnail of a 1920 px layer would be a third of a pixel, and every row would render as the same grey square. These are illustrations of each filter’s character; the document behind the dialog remains the honest preview. Rendering all nineteen costs a few milliseconds (the most expensive filter in the set is ~318 ms over 2 MP, which at 56×56 is well under a millisecond), and it happens off the render path so opening the dialog is never blocked by it. A layer with no pixels — an empty leaf, or a group with no raster of its own — falls back to plain icons rather than a column of blank squares.
- **Warp & Perspective Warp** (Effects ▸ Warp…): mesh transforms for a pixel layer, in nine presets (Arc, Arch, Bulge, Flag, Wave, Rise, Fish…) with Bend / Horizontal / Vertical shape controls, or a Perspective mode with four draggable corner handles. Both are built as a **displacement mesh and rendered by Liquify’s existing resampler** — nothing about inverse-mapped premultiplied bilinear sampling, transparent borders or the grid overlay is reimplemented; `warp.ts` only fills in the per-node backward offsets. The presets share `warpPoint` with warp-TEXT, so an Arc means the same thing on a text layer and on pixels. **Backward is the hard part.** A mesh node asks "for the pixel that lands here, where do I read from?", so both modes need the inverse of the map a human describes. Perspective inverts exactly and for free (solving the homography with the arguments swapped IS the inverse — measured at 0.007 px error, and shrinking with node spacing). The presets have no closed-form inverse and are solved numerically per node: a damped fixed-point iteration was tried first and **diverged to infinity** on strong bends combined with opposing distortion, so it uses Newton with a numerical Jacobian, bounded steps and a damped fallback where the warp folds. Verified across all nine presets at full strength: every reachable destination inverts to within 1e-3 (0 misses over 11,115 points), 549 destinations have no preimage at all — the warp is not onto its own bounding box, so those pixels are transparent by construction — and the solver never diverges. The result is **refitted inside the layer** rather than clipped: without that an Arc simply loses whatever it pushes past the top edge (measured: 1036 px of content gone; 0 with the refit). The preview renders at pane resolution and only the Apply pass runs at full resolution, so dragging a corner stays interactive on a large layer, and the whole transform is one undo step.
- **Measured and deliberately not built — a GPU stage for per-pixel filters.** Posterize/threshold/per-pixel stylize are trivial fragment shaders, but they are not a cost: a stroke on a posterize smart filter blocks **0 ms**, and so does a *settled* posterize param drag (the non-live path a GPU stage would actually serve, since live gestures already run at draft resolution) — against 54 ms for a blur in the same run. Shader plumbing, colour-space handling, a context-loss fallback and export-path divergence risk, to buy nothing measurable. The neighbourhood kernels are where the GPU case survives. The suite keeps a per-pixel scenario as a guard so the decision can be reopened on evidence rather than assumption.
- Remaining ceiling: *smart-filter* products still recompute whole-canvas, and a filter-worker reply currently invalidates every cached product (a blanket clear that also forces a full blit), so a filtered layer does not yet benefit from the region path above. Effect products likewise re-render whole-canvas on a miss — only the *change tracking* is region-scoped so far, not the product itself. The same reach is why leaf/group/clip-group products stay whole-canvas rather than tiled.

**Engine ceiling (deliberate, "v2-engine" territory)**
- **8-bit storage.** Layer pixels are Canvas 2D `ImageData` (8-bit per channel); the 16-bit path exists only inside the adjustment pipeline (emulated working spaces), the 32-bit float path only in the HDR merge/tone-map/export flow (the float map lives in memory, not in `.gproj`), and the GPU path only for the tone-LUT stage. Full 16/32-bit storage and compositing remain future tracks.
- **Layer space is document space.** Every layer raster is exactly the document's size and shares its origin, which is why cropping is always destructive: there is no "hide cropped pixels" mode, because there is nowhere for pixels outside the frame to live. Giving layers their own origin and extent would touch essentially every pixel path (266 uses of `this.w`, 45 full-canvas `getImageData` reads, 36 doc-sized allocations) plus the `.gproj` format, so it belongs with the other v2-engine tracks above. Content-aware straighten fill exists precisely because of this: it repairs the rotated corners rather than preserving what fell outside.
- **Content-aware fill is boundary-driven.** The synthesis is built for a hole enclosed by real pixels on every side. A straighten wedge is open along two canvas edges, so the fill seeds those pixels from the surrounding colour first and then adds texture near the boundary; deep inside a very large wedge the result is a smooth extension rather than invented detail. Fine on skies, gradients and foliage; a hard structure running into the corner will not be reconstructed. *The seeding is not a refinement but the fix for a real defect: without it the fill came out **~0.876× darker** than its surround, and the obvious explanation — the rotation's anti-aliased rim being sampled as source — was wrong, since a 2 px dilation changed the measurement by exactly nothing. Isolating the heal pass in Node with a synthetic wedge found the real cause: the healer assumes a blemish enclosed by real pixels on every side, and on a wedge open at the canvas edge it reaches into empty space.*

**Smart Filters (Spec 07 built)**
- Every layer/group can carry a non-destructive, re-editable **smart-filter stack** (Effects menu / Layers panel ▸ Smart Filters…): **Blur** (all nine Blur Gallery types, sharing the same kernel), **Sharpen** (Unsharp Mask), **Noise**, **Pixelate** (Mosaic), **Distort** (Twirl/Pinch/Wave), **Stylize** (Find Edges/Emboss/Posterize/Threshold), **High Pass**, **Median**, **Dust & Scratches**, **Reduce Noise**, **Lens Corrections**, **Dehaze**, **Clarity & Texture**, **Grain**, **Oil Paint**, **Halftone**, **Crystallize**, **Glitch** and **Drop Shadow (baked)** — each with enable/remove, **drag-reorder** in the stack list (one undo step per drop; Up/Down buttons remain), per-filter blend mode + opacity, one-step undo per edit, live document preview, cached via the render graph, serialized in `.gproj` (v7+), and bakeable via "Apply". The old placeholder menu items are now wired. **Liquify** shipped separately (Effects ▸ Liquify…, `Ctrl+Shift+X`) as its own warp-mesh tool rather than a stack filter.
- **Filter mask**: every stack can carry one grayscale mask that confines ALL its filters — white shows the filtered result, black keeps the original pixels, gray blends (premultiplied, so soft edges don't tint). Managed in the Smart Filters dialog (Add Mask / From Selection / Enable toggle / Paint / Delete) and shown as a dashed flask chip in the Layers panel (click targets it for painting, Shift-click disables/enables). It's a full paint surface: brush, pencil, eraser, fills, gradients, the blur/dodge/burn brushes and selection fills all work on it, with normal undo/redo. It duplicates with the layer, tracks canvas resizes/rotations/crops, is consumed by "Apply (Bake)", and saves as `filterMaskImage` in `.gproj` **v8** (v7 and older files still open).
- The in-app **documentation is curated by hand** (`app/lib/help.ts`): it describes what actually exists, but it is not generated from code — new features need a matching help entry. The **interactive onboarding tour + sample document** shipped 2026-07 (Help ▸ Interactive tour / Open sample document; Getting started remains the written walkthrough). **Keyboard Shortcuts** stays generated from the tool/menu registries.
